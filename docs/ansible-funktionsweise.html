Ansible-Code: Funktionsweise

Wie die Playbooks und Rollen in diesem Repository zusammenarbeiten – für alle, die den Code verstehen, ändern oder erweitern wollen. Betrieb und Bedienung stehen in den Betriebsdokumentationen (WordPress, Nextcloud).

Überblick

Ansible ist ein Push-Werkzeug: Ein Rechner (der Controller) verbindet sich per SSH mit den Servern und führt dort Schritt für Schritt aus, was in den Playbooks beschrieben ist. Auf den Servern läuft kein Agent, gebraucht werden nur SSH und Python. Die Beschreibung ist deklarativ: Ein Task sagt nicht „installiere Paket X“, sondern „Paket X soll vorhanden sein“ – ist es das schon, passiert nichts.

Controller (ansible-playbook, Repo, Vault-Passwort) │ SSH als root, Port 10022 (Host-Key wird geprüft) ├──► Blog-Server blog.yml / blog-update.yml └──► Nextcloud-Server nextcloud-k3s.yml / nextcloud-update.yml │ └─ auf jedem Server: Host-Dienste (nftables, SSH, fail2ban, Monitoring …) + K3s mit den Anwendungen als Kubernetes-Workloads

Das Repository steuert zwei Arten von Servern, beide AlmaLinux 9 mit einem K3s-Einzelknoten-Cluster:

  • Blog (Gruppe blog): WordPress, MariaDB und Redis laufen komplett in K3s.
  • Nextcloud (Gruppe nextcloud): Nextcloud, Collabora und notify_push laufen in K3s, MariaDB und Redis als Dienste auf dem Host.

Alles Gemeinsame – Härtung, Firewall, Monitoring, K3s selbst – steckt in Rollen mit dem Präfix common_ und wird von beiden Playbooks genutzt.

Inventory & Variablen

Das Inventory (inventory/hosts.yml) ordnet jeden Server einer Gruppe zu. Die Playbooks zielen auf eine Gruppe (hosts: blog), mit --limit <host> wählt man einen Server daraus.

Variablen kommen aus mehreren Stellen. Gilt eine Variable an mehreren Stellen, gewinnt die mit dem höheren Rang. Für dieses Repo sind diese Stufen wichtig (von niedrig nach hoch):

RangOrtWofür hier
1roles/<rolle>/defaults/main.ymlStandardwerte einer Rolle, z. B. clamav_profiles
2inventory/group_vars/all/*.ymlfür alle Server gleich: Versionen, Pfade, Ressourcen-Defaults
3inventory/host_vars/<host>/*.ymlpro Server: Hostnamen, IPs, Passwörter, eigene Ressourcen
4Parameter an der Rolle im Playbook{ role: common_clamav, clamav_target: wordpress }
5register / set_factErgebnisse von Tasks während des Laufs
6-e auf der Kommandozeileschlägt alles – für Tests und Einmaliges
Beispiel nextcloud_fpm_mem_limit: "4Gi" steht in group_vars/all/main.yml. Ein Server mit mehr RAM setzt in seiner host_vars/<host>/vars.yml einen höheren Wert – der gewinnt, weil host_vars einen höheren Rang hat. Alle anderen Server behalten den Default.

Die vollständige Rangfolge hat über 20 Stufen (Ansible-Doku: „Variable precedence“). In der Praxis reicht die Tabelle oben; die meisten schwer erklärbaren Effekte entstehen, wenn dieselbe Variable unerwartet an zwei Stellen gesetzt ist.

Vault

vault.yml ist mit ansible-vault verschlüsselt. Ansible entschlüsselt sie beim Lauf mit dem Vault-Passwort (--ask-vault-pass oder eine Datei .vault_pass, die nie ins Repo kommt). Für das Bearbeiten: ansible-vault edit inventory/host_vars/<host>/vault.yml.

Eingaben werden geprüft

Jede Rolle, die Werte aus host_vars braucht, beschreibt sie in meta/argument_specs.yml – Typ, Beschreibung, Pflicht ja/nein, und no_log für Secrets. Ansible prüft das beim Start der Rolle: fehlt z. B. ein Eintrag im Vault, bricht der Lauf sofort mit dem Variablennamen ab statt mitten in der Installation. „Pflicht“ ist nur, was jeder Server, auf dem die Rolle läuft, tatsächlich hat – gemeinsame Rollen wie common_grafana lesen auf dem Blog blog_hostname, auf Nextcloud nextcloud_hostname.

Gut zu wissen Diese Prüfungen tragen das Tag always: Sie laufen auch bei --tags … für alle Rollen mit. Sie sind schnell und rein lesend.

Versionen an einer Stelle

inventory/group_vars/all/versions.yml enthält jede Version, die installiert oder ausgerollt wird: K3s, Helm, Calico, die Helm-Charts, alle Container-Images, WP-CLI (mit Prüfsumme), die Monitoring-Programme und die MariaDB-Repository-Serie der Nextcloud-Server. Oben stehen die Werte kompakt, darunter die Begründungen und die Historie je Eintrag.

  • Immer exakt, nie latest oder ein mitwandernder Tag: K3s zieht Images mit IfNotPresent – ein mitwandernder Tag bleibt still auf dem Stand, der zufällig im Cache liegt.
  • Nicht in der Datei: die Ansible-Collections (requirements.yml, dort liest sie ansible-galaxy) und die Versionen der Prüfwerkzeuge (Pre-Commit, GitHub Action).
  • Renovate schlägt Erhöhungen dieser Zeilen als Pull Request vor (siehe Werkzeuge).

Die Playbooks

blog.yml und nextcloud-k3s.yml

Beide bestehen aus einem Play mit einer Liste von Rollen. Die Reihenfolge ist Absicht:

  1. common_version_check – zeigt vorab installierte und verfügbare Versionen.
  2. Pakete, SSH, Firewall, sysctl, CIS-Härtung – die Basis, bevor irgendetwas lauscht.
  3. common_selinux vor dem Deploy – die HostPath-Verzeichnisse brauchen ihr SELinux-Label, bevor ein Container sie benutzt.
  4. common_k3s, common_calico, dann das Deploy der Anwendung (blog_k3s_deploy bzw. next_k3s_deploy). Die Pods starten im Hintergrund.
  5. Monitoring, fail2ban, Mail, automatische Updates, rkhunter, ClamAV, auditd, Monit – laufen, während die Pods hochfahren (spart Minuten).
  6. Konfiguration in der Anwendung (blog_wordpress bzw. next_config, per kubectl exec) – jetzt sind die Pods bereit.
  7. *_verify – Rauchtests mit farbigem Bericht und Mail.
  8. common_aide_refresh immer zuletzt – erneuert die AIDE-Basis, damit die nächtliche Prüfung die eigenen, gewollten Änderungen nicht als Alarm meldet.

Jede Rolle hat ein Tag mit ihrem Namen. --tags common_k3s,blog_k3s_deploy führt nur diese Rollen aus. Die zusammengelegten Rollen behalten die alten Tags (blog_clamav, next_selinux …), damit gewohnte Aufrufe weiter funktionieren.

Die Update-Playbooks

blog-update.yml und nextcloud-update.yml sind für den laufenden Betrieb gedacht und fassen den Host nicht an. Beide verlangen --limit, Nextcloud arbeitet mit serial: 1 einen Server nach dem anderen ab und stoppt beim ersten Fehler.

Vorprüfung (außerhalb des Blocks) gesund? sonst Abbruch, nichts wird angefasst block: Images der Deployments neu ziehen, Digest mit den laufenden Pods vergleichen nur Deployments mit neu gebautem Image neu starten (Rolle common_image_refresh) Blog: nächtlichen Update-Job jetzt starten (DB-Dump zuerst), auswerten Nextcloud: occ upgrade, occ app:update --all, zweiter Neustart wegen OPcache Abschlussprüfung (Nextcloud: kein Wartungsmodus, kein ausstehendes DB-Upgrade) rescue: Zustand sammeln (occ status, Pods, Events, nextcloud.log / neuester DB-Dump) Nextcloud: Wartungsmodus nur aus, wenn das Upgrade selbst fertig ist deutlich abbrechen – kein weiterer Server

Rollen

Eine Rolle ist eine abgeschlossene Aufgabe mit festem Verzeichnisaufbau (siehe Aufbau). Große Rollen sind in thematische Dateien aufgeteilt, die tasks/main.yml per import_tasks in fester Reihenfolge einbindet (z. B. blog_wordpress: install, security_muplugin, plugins, appearance, ai_disclosure, settings, updates).

Die Rollen im Einzelnen

Jede Rolle in drei Teilen: Was sie macht, Warum es sie gibt, und Wie sie arbeitet – als Schrittfolge mit den Ansible-Bausteinen (→ = danach). Die Reihenfolge ist die der Playbooks. Ausführlicher, Task für Task, steht es als Kommentar am Anfang jeder Datei unter roles/<rolle>/tasks/.

Vorbereitung und Grundsystem

common_version_check (beide)

Was: Zeigt am Anfang jedes Laufs, welche Versionen von K3s, Helm, nginx-ingress und cert-manager installiert, festgelegt und neu verfügbar sind. Warum: Man sieht vor jedem Lauf, ob eine Festlegung in versions.yml veraltet oder noch nicht ausgerollt ist.

Wie: Versionen ermitteln (command auf dem Server, uri gegen die GitHub-API) → mit einem ersten set_fact in eine einheitliche Schreibweise bringen (regex_search, from_json) → mit einem zweiten set_fact vergleichen (== ergibt wahr/falsch) → mit debug als farbigen Bericht ausgeben. Rein lesend, bricht nie ab.

blog_packages / next_packages (je Stack)

Was: Hostname, Paketquellen (EPEL; bei Nextcloud auch CRB und MariaDB), Systemupdate, Grundpakete. Warum: Ohne sie fehlen allen späteren Rollen Werkzeuge und Abhängigkeiten.

Wie: Hostname setzen (hostname) → Paketquellen einrichten (erst dnf repolist lesen, nur Fehlendes aktivieren) → alles außer dem Kernel aktualisieren (dnf name: "*" state: latest; der Kernel lässt sich in der abgesicherten SSH-Sitzung nicht installieren – ProtectKernelModules aus common_ssh –, er kommt nachts über dnf-automatic) → prüfen, ob ein Neustart nötig ist (needs-restarting, über systemd-run), nur dann reboot → Pakete installieren → ungenutzte Dienste abschalten und maskieren.

common_ssh (beide)

Was: SSH auf Port 10022, gehärtete sshd_config (nur Schlüssel), SELinux-Label für den Port, Mail-Alarm bei jeder interaktiven Anmeldung. Warum: Nimmt den automatisierten Angriffen auf Port 22 die Grundlage und schließt Passwort-Logins aus. Ein systemd-Drop-in legt außerdem eine Sandbox um sshd, die jede SSH-Sitzung erbt: keine Kernel-Module, keine Kernel-Werte – das geht nur noch bewusst über systemd-run (Details in den Betriebs-Dokus, „Wichtige Sicherheitshinweise“).

Wie: merken, ob dies der erste Lauf ist (set_fact ssh_first_run) → SELinux-Portliste lesen, Label nur bei Bedarf setzen → Konfiguration und Drop-ins kopieren (copy, notify) → Handler-Kette am Ende: mit sshd -t prüfen → sshd neu starten (async, weil die eigene Verbindung abreißt) → reset_connection → wait_for_connection → zuletzt den Login-Alarm einrichten: Skript aus Vorlage, systemd-Timer alle 2 Minuten, der neue interaktive Anmeldungen aus wtmp per Mail meldet.

common_firewall (beide)

Was: nftables-Regeln für IPv4/IPv6, auf Wunsch Länderfilter für SSH. Warum: Nur ausdrücklich Erlaubtes kommt durch; fail2ban bekommt seine Sperrlisten.

Wie: DHCP oder statisch ermitteln (nmcli lesen → set_fact) → optional Länderliste bauen → Regelwerk aus der Vorlage schreiben, vorher geprüft (template validate: nft -c) → Neuladen auf die eigene Tabelle beschränken (systemd-Drop-in) → Handler lädt nftables neu und lässt fail2ban seine Sperren neu setzen (listen). Erster Lauf: Neustart statt Live-Aktivierung (include_tasks … when).

common_sysctl (beide)

Was: Kernel-Parameter (TCP BBR, Timeouts, Warteschlangen, CIS-Netzwerkhärtung) und Transparent Huge Pages auf madvise. Warum: Schnellerer Webserver, bekannte Netzwerk-Schwachstellen geschlossen.

Wie: Modul tcp_bbr laden und für den Boot eintragen → Werte als Dateien nach /etc/sysctl.d/ (template, dauerhaft) → sofort anwenden (sysctl --system über systemd-run, weil die abgesicherte SSH-Sitzung keine Kernel-Werte schreiben darf) → kleine systemd-Unit setzt THP bei jedem Boot.

common_cis_hardening (beide)

Was: Die gefahrlos umsetzbaren Punkte des CIS-Benchmarks: AIDE, gesperrte Kernel-Module, Journal, keine Core-Dumps, cron/sudo-Rechte, Mount-Optionen. Warum: Weniger Angriffsfläche; riskante Punkte (PAM, GRUB, Krypto-Richtlinie) bleiben bewusst draußen.

Wie: eine Reihe kleiner, unabhängiger Gruppen, jede nach dem Muster „Zustand prüfen → nur bei Bedarf ändern“: z. B. AIDE-Datenbank nur anlegen, wenn sie fehlt (stat → when) → sudoers nur nach Prüfung schreiben (validate: visudo -cf) → Mount-Optionen in fstab schreiben und sofort aktiv machen (mount state: mounted).

common_selinux (beide, Profil selinux_target)

Was: SELinux im Modus „enforcing“ und die Host-Verzeichnisse, die als Speicher in die Pods kommen. Warum: Container dürfen nur in Dateien mit dem Typ container_file_t schreiben.

Wie: Profil wählen (selinux_profiles[selinux_target]) → Verzeichnisse mit Besitzer und Rechten anlegen (file, loop) → Regel dauerhaft eintragen (semanage fcontext; „already defined“ gilt weder als Fehler noch als Änderung) → auf vorhandene Dateien anwenden (restorecon).

Nur Nextcloud: Datenbank und Cache auf dem Host

next_mariadb (Nextcloud)

Was: MariaDB auf dem Host: systemd-Härtung, Slow-Query-Log, Rotation, Datenbank, Benutzer. Warum: Nextcloud braucht eine Datenbank, die nur für die Pods erreichbar ist.

Wie: prüfen, ob die Nextcloud-Datenbank schon existiert (register db_check) → nur beim ersten Lauf: Root-Passwort, Datenbank und Benutzer anlegen (when: db_check.rc != 0) → bei jedem Lauf: anonyme Konten und die Test-Datenbank entfernen, Exporter-Benutzer anlegen oder korrigieren (community.mysql, idempotent, no_log).

next_redis (Nextcloud)

Was: Redis für die Pods erreichbar machen und mit Passwort sichern. Warum: Redis hält Dateisperren und Sitzungen von Nextcloud.

Wie: prüfen, ob das Passwort im Vault steht (assert) → drei Zeilen in redis.conf setzen (lineinfile, notify) → Neustart sofort statt am Ende (meta: flush_handlers) → warten, bis der Port antwortet (wait_for).

Kubernetes und die Anwendung

common_k3s (beide)

Was: K3s, Helm samt Plugin helm-diff, cert-manager (Let's Encrypt) und der F5-nginx-Ingress. Die mitgelieferten K3s-Bausteine, die hier keiner braucht (Traefik, ServiceLB, local-storage), sind abgeschaltet. Warum: Das ist die Plattform, auf der Blog und Nextcloud laufen. Was nicht läuft, kann auch nicht angegriffen werden.

Wie: installierte Version lesen (register) → Binary nur laden, wenn sie von k3s_version abweicht (get_url … when, notify) → Neustart sofort (flush_handlers) → warten, bis die API antwortet (until) → Helm genauso → helm-diff nur laden, wenn die Version von helm_diff_version abweicht (Prüfsumme in get_url) → Charts installieren (kubernetes.core.helm ändert nur bei anderer Chart-Version oder anderen Werten).

common_calico (beide)

Was: Calico nur im Policy-Modus – das Netz macht weiter Flannel, Calico setzt die NetworkPolicies durch. Warum: Ohne Calico würden alle NetworkPolicies still ignoriert.

Wie: Vorlage auf dem Controller rendern (lookup('template')) → in Kubernetes-Objekte zerlegen (from_yaml_all) → per API anwenden (kubernetes.core.k8s apply, „changed“ nur bei echter Abweichung) → nur dann auf die Pods warten (rollout status … when changed). Dieses K8s-Apply-Muster nutzen 26 Tasks im Repo.

blog_k3s_deploy / next_k3s_deploy (je Stack)

Was: Alle Kubernetes-Objekte der Anwendung: Namespace, Secrets, ConfigMaps, Deployments, Services, Ingress, CronJobs, NetworkPolicies, Image-Richtlinie (bei Nextcloud dazu Collabora, notify_push, App-Abgleich). Warum: Damit die Anwendung jederzeit aus dem Repo neu aufgebaut werden kann.

Wie: pro Komponente eine Vorlage und eine Task-Datei, in Abhängigkeits-Reihenfolge (import_tasks) → jede mit dem K8s-Apply-Muster anwenden → nur wenn sich etwas geändert hat, auf die neuen Pods warten → Nextcloud: MariaDB/Redis auf dem Host als „externe Services“ (Service ohne Selector + Endpoints auf die Host-IP).

Überwachung

common_node_exporter / common_mysqld_exporter (beide / nur Nextcloud)

Was: Stellen Kennzahlen des Hosts bzw. der Host-MariaDB lokal bereit (127.0.0.1:9100 / :9104). Warum: Prometheus holt sie dort ab; von außen ist nichts erreichbar.

Wie: installierte Version lesen → Archiv nur bei abweichender Version laden, entpacken, installieren (get_url → unarchive → copy, im Probelauf übersprungen) → systemd-Unit + Sandbox-Drop-in schreiben (notify) → Handler laden systemd neu und starten den Dienst einmal neu. Der MariaDB-Exporter liest sein Passwort aus einer Datei, die nur er lesen darf (no_log).

common_prometheus (beide)

Was: Sammelt die Kennzahlen aller Exporter und hebt sie 30 Tage auf, nur lokal erreichbar. Warum: Grundlage für Grafana-Kurven und Alarme.

Wie: wie bei den Exportern (Version prüfen → nur bei Abweichung laden) → Konfiguration aus der Vorlage, die je Stack die passenden Exporter einträgt (template) → Unit und Sandbox → genau ein Neustart am Ende, egal wie viele Dateien sich geändert haben (Handler).

common_grafana (beide)

Was: Grafana mit Prometheus-Datenquelle, drei Dashboards und Alarm-Mails, erreichbar unter /grafana/. Warum: Kurven und Warnungen, ohne dass Prometheus selbst nach außen muss.

Wie: Paket installieren, einzelne Zeilen in grafana.ini setzen (lineinfile) → starten und warten, bis die API antwortet (uri … until) → per HTTP-API „erst nachsehen, dann anlegen“ (GET registrieren → POST nur when es fehlt) → Dashboards laden und importieren → Alarmregeln per kleinem Python-Skript.

Schutz, Mail und Wartung

common_fail2ban (beide)

Was: Sperrt IP-Adressen, die SSH oder die Logins angreifen oder das System abtasten. Warum: Automatisierte Angriffe enden nach wenigen Versuchen statt nie.

Wie: eigene Sperr-Aktion (schreibt in die nftables-Sets der Firewall), fünf Filter und jail.local mit sieben Jails aus Vorlagen (template, notify) → Dienst starten → ein Timer lädt die HTTP-Jails neu, sobald der Ingress-Pod eine neue Log-Datei anlegt.

common_msmtp (beide)

Was: msmtp als schlanker Ersatz für sendmail. Warum: cron, rkhunter, ClamAV, dnf-automatic und die Prüfberichte können Mails verschicken.

Wie: Paket installieren → /etc/msmtprc aus der Vorlage (Relay, Port, Zugang aus dem Vault; Rechte 0600) → Log-Datei einmalig anlegen (file state: touch mit preserve, damit sie nicht jedes Mal als geändert gilt). Kein Dienst: jedes Programm startet msmtp selbst.

common_dnf_automatic (beide)

Was: Spielt nachts Sicherheitsupdates ein und startet um 03:30 neu, wenn nötig. Warum: Sicherheitslücken werden geschlossen, ohne dass jemand daran denken muss.

Wie: zwei Zeilen in automatic.conf (nur Sicherheitsupdates, wirklich installieren) → Timer per Drop-in auf 01:00 verlegen (neu gestartet nur, wenn sich der Drop-in geändert hat: register → is changed) → zwei cron-Einträge: Neustart bei Bedarf und Kontroll-Mail um 06:00.

common_rkhunter (beide)

Was: Sucht nachts nach Rootkits und veränderten Systemdateien, mailt nur bei Funden. Warum: Frühwarnung, falls der Server kompromittiert wurde.

Wie: Optionen setzen (lineinfile in einer loop über Schlüssel/Wert) → Vergleichsdatenbank aufbauen (--propupd) → nächtlichen cron-Eintrag anlegen, den doppelten Scan des Pakets entfernen → dnf-Plugin, das die Datenbank nach jedem Update erneuert (sonst Fehlalarm).

common_clamav (beide, Profil clamav_target)

Was: Nächtlicher Virenscan der hochgeladenen Dateien (Blog: Uploads, Nextcloud: Nutzerdaten), Mail nur bei Funden. Warum: Schadsoftware in fremden Uploads fällt spätestens am nächsten Morgen auf.

Wie: Profil wählen (set_fact clamav: profiles[target]) → Signaturen einmalig laden (creates:), danach aktualisiert sie der freshclam-Dienst → Ausschluss-Muster für Mediendateien per Jinja erzeugen → Scan-Skript schreiben (copy mit Jinja-{% if %}) → cron-Eintrag.

blog_visitor_stats (Blog)

Was: Zählt jede Nacht anonym die Besucher des Vortags aus dem Ingress-Log, speichert nur Zahlen. Warum: Entwicklung über Monate, obwohl K3s die Logs nur wenige Tage aufhebt – keine IP verlässt den Server.

Wie: Skript und Länder-Datenbank-Updater kopieren → zwei systemd-Timer aus Vorlagen (flush_handlers vor dem Start) → einmalig Länder-Datenbank laden und die noch vorhandenen Tage nachtragen (creates:, loop über 1–5 Tage).

common_auditd (beide)

Was: Kernel protokolliert sicherheitsrelevante Vorgänge (Benutzerdateien, sudo, SSH-Konfiguration, K3s-Schlüssel …). Warum: Spuren für spätere Nachforschungen und eine Mail bei Ereignissen, die nie vorkommen sollten.

Wie: Regeldatei kopieren → Handler lädt sie in den Kernel (augenrules --load) → Melde-Skript und cron alle zehn Minuten, das nur die kritischen Schlüssel mailt.

common_logrotate (beide)

Was: Rotationsregeln für Logs ohne oder mit unvollständigen Regeln (Grafana, Prometheus, fail2ban, rkhunter). Warum: Sonst wachsen sie unbegrenzt.

Wie: vier copy-Tasks nach /etc/logrotate.d/ – kein Neustart nötig, logrotate liest sie beim nächsten täglichen Lauf.

common_monit (beide)

Was: Wachhund für Dienste, Firewall, Pods, Zertifikate, Speicher und Backups; startet fail2ban bei Ausfall neu. Warum: Mailt nur bei Zustandsänderungen – jede Mail bedeutet also etwas.

Wie: prüfen, ob die Mail-Zugangsdaten da sind (assert) → ermitteln, welche Dienste es auf diesem Host gibt (systemctl cat in einer loop → zip + selectattr) → Prüfskripte und Konfiguration aus Vorlagen → Konfiguration mit monit -t prüfen → starten.

Anwendung einstellen und prüfen

blog_wordpress (Blog)

Was: WordPress im laufenden Pod per WP-CLI: Installation, Härtungs-Plugin, Plugins, Menü/CSS, KI-Hinweis, Einstellungen, Updates. Warum: Die Einrichtung des Blogs ist reproduzierbar und Updates laufen bei jedem Lauf mit.

Wie: überall „Zustand lesen → nur Nötiges ändern“: z. B. Plugin-Liste einmal lesen (from_json) → nur fehlende installieren (difference), nur inaktive aktivieren (selectattr) → PHP-Dateien erst als .new schreiben, nur bei anderer Prüfsumme austauschen → Versionen vor und nach den Updates vergleichen, nur dann neu starten.

next_config (Nextcloud)

Was: Nextcloud im laufenden Pod per occ: Domains, URL, Mail, Datenbank-Pflege, Office- und Vorschau-App, Collabora-Anbindung, Passwortrichtlinie. Warum: Die Einstellungen stehen im Repo statt nur in der laufenden Instanz.

Wie: für jeden Wert „get → vergleichen → set“: aktuellen Wert lesen (occ config:…:get, register) → nur schreiben, when er abweicht (changed_when: true) → so meldet ein unveränderter Lauf nichts, und ein von Hand verstellter Wert wird zurückgesetzt und als Änderung angezeigt. Als letzter Schritt dieselbe Kette für die Passwortrichtlinie (password_policy.yml): App einschalten → Werte lesen → abweichende alte Werte löschen → mit Typ neu setzen (--type=integer|boolean).

blog_verify / nextcloud_verify (je Stack)

Was: Rauchtests nach dem Lauf: Dienste, Pods, HTTPS, Zertifikat, Header, gesperrte Pfade, Datenbank/Cache. Warum: Ein Lauf, der „ok“ meldet, heißt noch nicht, dass die Seite funktioniert.

Wie: alle Prüfungen nur sammeln (register _v_*, failed_when: false) → per set_fact in wahr/falsch umrechnen (_r_*) → zählen, Bericht ausgeben, Mail schicken → erst ganz am Ende assert auf die kritischen Punkte. Gleiches Muster wie beim Versions-Check: erst erheben, dann aufbereiten, dann bewerten.

common_aide_refresh (beide)

Was: Erneuert als letzte Rolle die AIDE-Vergleichsdatenbank, wenn der Lauf überwachte Dateien geändert hat. Warum: Sonst meldet AIDE in der nächsten Nacht die eigenen Änderungen des Laufs als Fund.

Wie: ein einziger Scan vergleicht und schreibt die neue Datenbank (aide --update) → Rückgabewert auswerten (1–7 = Unterschiede, 0 = gleich, ab 14 = Fehler) → nur bei Unterschieden die neue Datenbank aktivieren – das ist der einzige Task, der „changed“ meldet.

Hilfsrollen (nicht direkt im Playbook)

common_verify – Die gemeinsamen Prüfungen für Host, Kubernetes und HTTP. Wie: wird von den Verify-Rollen per import_role … tasks_from eingebunden, sammelt nur Ergebnisse (_v_*); das Urteil fällt die aufrufende Rolle.

common_image_refresh – Für die Update-Playbooks: Welche Deployments haben ein neu gebautes Image? Wie: ein Python-Skript (script) lädt jedes Image neu und vergleicht den Digest mit dem laufenden Pod → Ergebnis als JSON → set_fact → neu gestartet wird nur, was wirklich neu gebaut wurde.

Was bei einem Lauf passiert

  1. Facts sammeln – nur gather_subset: min; mehr wird nirgends gebraucht.
  2. Pro Rolle: zuerst die Argument-Prüfung, dann die Tasks der Reihe nach. Jeder Task meldet ok (nichts zu tun), changed (etwas geändert), skipped (Bedingung nicht erfüllt) oder failed.
  3. Handler: Ein Task mit notify: Reload nftables merkt den Handler nur vor, wenn er changed meldet. Handler laufen gesammelt am Ende des Plays – oder früher, wo eine Rolle meta: flush_handlers setzt (z. B. K3s muss neu gestartet sein, bevor es weitergeht). Mehrere Handler können mit listen: auf dasselbe Ereignis reagieren (nftables neu laden, danach fail2ban die Sperren neu setzen lassen).
  4. Zusammenfassung (PLAY RECAP) mit ok/changed/failed pro Server und die Zeiten pro Task.

Probelauf: --check --diff

Mit --check ändert Ansible nichts, sondern meldet, was es ändern würde; --diff zeigt die Unterschiede. Damit das hier aussagekräftig ist:

  • Reine Abfragen (Versionen, occ config:system:get, kubectl get, systemctl is-active) haben check_mode: false und laufen auch im Probelauf – sonst hätten spätere Tasks keine Daten.
  • Schreibende Befehle werden übersprungen. Wo das eine anstehende Änderung verstecken würde, meldet ein eigener Task sie (z. B. „mail_smtphost would be updated“).
  • Die Kubernetes-Objekte vergleicht das k8s-Modul per Server-Side-Dry-Run mit dem Cluster – der Diff zeigt genau die geänderten Felder.

Kubernetes aus Ansible

Die Anwendungen sind Kubernetes-Objekte. Ansible erzeugt sie aus Jinja2-Templates und übergibt sie mit dem Modul kubernetes.core.k8s direkt an die K3s-API:

- name: Redis | Apply Deployment + Service
  kubernetes.core.k8s:
    kubeconfig: "{{ k3s_kubeconfig }}"
    state: present
    apply: true
    definition: "{{ item }}"
  loop: "{{ k8s_objects if ansible_diff_mode else [k8s_objects] }}"
  loop_control:
    label: "{{ (item.kind ~ '/' ~ item.metadata.name) if item is mapping else ((item | length) ~ ' objects') }}"
  vars:
    k8s_objects: "{{ lookup('ansible.builtin.template', 'redis-deployment.yml.j2') | ansible.builtin.from_yaml_all | select | list }}"
  register: redis_apply
  • lookup('template', …) rendert das Template im Speicher; from_yaml_all zerlegt es in die einzelnen Objekte. Nichts landet in /tmp – auch keine Secrets.
  • apply: true verhält sich wie kubectl apply (über die Annotation last-applied-configuration), ist also mit den bestehenden Objekten kompatibel.
  • Ein Aufruf oder einer pro Objekt: Bei normalen Läufen gehen alle Objekte eines Templates in einem Aufruf an die API (Calico: unter 2 statt ~30 Sekunden). Nur mit --diff (also bei check-drift.sh) läuft die Schleife pro Objekt – nur so zeigt der Diff die Änderung jedes Objekts, und die Ausgabe nennt Deployment/redis, Service/redis.
  • Das Modul meldet changed nur, wenn sich am Objekt wirklich etwas ändert. Folgetasks wie „Rollout abwarten“ hängen an redis_apply.changed.
  • Abfragen laufen über kubernetes.core.k8s_info (gibt es das Secret schon?).
  • Die Helm-Charts (cert-manager, nginx-ingress) verwaltet kubernetes.core.helm: Es vergleicht Chart-Version und Werte des laufenden Releases und aktualisiert nur bei einem Unterschied. Mit dem Plugin helm-diff zeigt --check --diff auch bei Charts, welche Werte sich ändern würden.
  • Voraussetzung auf dem Server: das Paket python3-kubernetes (installiert common_k3s); auf dem Controller die Collection kubernetes.core ≥ 6.5.0 (Helm 4).

Was in den Containern passiert – occ für Nextcloud, wp-cli für WordPress (immer als www-data) – läuft weiterhin über k3s kubectl exec.

Idempotenz & „changed“

Idempotent heißt: Der zweite Lauf hintereinander ändert nichts mehr und meldet überall changed=0. Erst dann bedeutet ein changed etwas – und ein Probelauf zeigt verlässlich, was ein echter Lauf tun würde. Die Muster in diesem Code:

MusterBeispiel
Modul statt Befehlansible.builtin.dnf, file, template, kubernetes.core.k8s wissen selbst, ob etwas zu tun ist
creates:freshclam nur, solange /var/lib/clamav/freshclam.dat fehlt
changed_when aus der Ausgabeocc upgrade ist nur „changed“, wenn er „Update successful“ meldet
lesen – vergleichen – schreibendie neun Mail-Werte von Nextcloud: erst config:system:get, nur Abweichungen setzen; der Exporter-Datenbankbenutzer: erst Passwort-Hash und Rechte prüfen
changed_when: falsenur für echte Abfragen – nie für einen Befehl, der schreibt
Die Falle Ein command-Task, der jedes Mal schreibt und changed_when: false hat, sieht harmlos aus, versteckt aber jede Änderung. Ein Task, der jedes Mal changed meldet, macht dagegen jeden Lauf zum „Drift“. Beides ist hier beseitigt; scripts/check-drift.sh zeigt sofort, wenn so etwas wieder auftaucht.

Fehlerbehandlung

  • ansible.builtin.assert prüft Voraussetzungen und bricht mit einer verständlichen Meldung ab (Update ohne --limit, Nextcloud nicht gesund, Exporter-Passwort fehlt im Vault).
  • failed_when legt fest, was ein Fehler ist – z. B. ist „already installed“ bei occ app:install keiner.
  • block/rescue in den Update-Playbooks: Scheitert ein Schritt im Block, läuft der rescue-Teil. Er hat Zugriff auf ansible_failed_task und ansible_failed_result und gibt Task-Name, Fehlermeldung und Ausgabe aus.
  • Die Vorprüfung steht bewusst außerhalb des Blocks: Das Rescue soll nur Zustände behandeln, die der Lauf selbst verursacht hat. Ist Nextcloud schon vorher im Wartungsmodus, lehnt das Playbook ab, statt ihn „aufzuräumen“.

Secrets

  • Passwörter stehen nur in vault.yml (verschlüsselt, gitignored).
  • no_log: true an jedem Task, der sie verarbeitet – auch an k8s_info-Abfragen von Secrets, weil das Ergebnis die Daten enthält. In Schleifen kann no_log pro Eintrag gelten (no_log: "{{ item.secret | default(false) }}").
  • Argument-Specs markieren Vault-Werte mit no_log – getestet: sie erscheinen weder bei -vvv noch in einer Fehlermeldung.
  • Kubernetes-Secrets werden im Speicher gerendert und direkt an die API übergeben, nie als Datei auf dem Server.
  • Werte an occ gehen per argv, nicht über eine Shell-Zeile – ein Anführungszeichen im Passwort kann den Befehl nicht verändern.
  • Vor jedem Commit sucht gitleaks nach Schlüsseln und Tokens (siehe nächster Abschnitt).

Tests

tests/k8s/run.sh – Kubernetes-Rollen ohne Server

Startet einen K3s (gleiche Version wie k3s_version) als reinen API-Server in Podman, spielt die Manifeste erst mit den Rollen aus main ein (der Stand der Server), dann mit dem Arbeitsstand: Probelauf, echter Lauf, zweiter echter Lauf, Probelauf. Schlägt fehl, wenn der zweite Lauf noch etwas ändert, ein Pod neu ausgerollt würde, ein Helm-Release eine neue Revision bekommt – oder wenn eine absichtlich geänderte Image-Version nicht erkannt wird. Ohne laufende Pods: was in den Containern passiert (occ, wp-cli), ist nicht Teil dieses Tests.

tests/update/run.sh – Fehlerfälle der Update-Playbooks

14 Szenarien gegen nachgebaute kubectl/crictl: gesund, neu gebautes Image, Wartungsmodus schon vorher an, Upgrade bricht ab, Fehler nach fertigem Upgrade, Rollout hängt, Update-Job scheitert, Blog läuft nicht, Probelauf. Geprüft werden Exit-Code, die ausgeführten Befehle und der Wartungsmodus danach.

scripts/check-drift.sh – gegen einen echten Server

scripts/check-drift.sh nextcloud-k3s.yml <host> --ask-vault-pass
scripts/check-drift.sh blog.yml <host> --tags blog_k3s_deploy --ask-vault-pass

Probelauf mit --check --diff; ausgegeben werden nur die Tasks, die etwas ändern würden, mit lesbarem Diff (Verwaltungsfelder von Kubernetes ausgeblendet). Exit-Code 0 = kein Drift. Direkt nach einem echten Lauf muss „NO DRIFT“ kommen – sonst ist ein Task nicht idempotent.

Arbeitsablauf für eine Änderung

  1. Ändern – Rolle, Template oder versions.yml.
  2. ansible-lint (läuft beim Commit ohnehin).
  3. Betrifft es Kubernetes-Rollen: tests/k8s/run.sh; betrifft es ein Update-Playbook: tests/update/run.sh.
  4. scripts/check-drift.sh <playbook> <host> – zeigt, was der echte Lauf ändern wird. Passt das zur Absicht?
  5. Echter Lauf, zuerst auf einem Server, mit --tags auf das Nötige beschränkt.
  6. Noch einmal check-drift.sh → „NO DRIFT“.
  7. Commit (die Hooks prüfen Lint und Secrets), Push.
Versions-Update Renovate-PR (oder eigene Änderung in versions.yml) lesen → Release-Notes der Komponente prüfen → check-drift.sh → Rollout mit dem passenden Tag (z. B. --tags common_k3s,blog_k3s_deploy) → mergen.

Stolperfallen

  • Gleiche Variable an zwei Stellen – Rangfolge prüfen (ansible -m debug -a var=… gegen den Host zeigt den Wert, der tatsächlich gilt).
  • item in verschachtelten Schleifen – eine äußere Schleife um include_role braucht loop_control: loop_var: …, sonst überschreiben die Schleifen der Rolle item.
  • Schleife und when – die Schleife wird vor der Bedingung ausgewertet; ein Template in loop: muss also auch dann rendern können, wenn when false ist.
  • Tags und include_role – Tags vererben sich nur bei import_* (statisch), nicht bei include_* (dynamisch).
  • /tmp ist noexec (CIS) – Skripte dort mit sh skript aufrufen, nicht direkt ausführen.
  • Modulnamen mit Collection – ansible.builtin.ini_file „funktionierte“ nur über eine Weiterleitung zu community.general. ansible-lint findet so etwas (syntax-check[unknown-module]).
  • Cron-Einträge werden über ihren name erkannt – wer den Namen ändert, hat danach zwei Einträge.

Lernpfad

  1. Lesen mit Ziel: eine Rolle wählen (z. B. common_clamav) und für jeden Task erklären, warum er so aussieht – Modul, Bedingung, changed_when.
  2. Idempotenz selbst erleben: eine Rolle zweimal per --tags laufen lassen, der zweite Lauf muss changed=0 zeigen; dann check-drift.sh.
  3. Eine Rolle selbst schreiben – ohne Vorlage, mit argument_specs, Handler und Test; danach mit einer bestehenden vergleichen.
  4. Werkzeuge: ansible-doc <modul>, ansible <host> -m setup, --start-at-task, --step, -vvv.
  5. Strukturiertes Ziel: Die Prüfung RHCE (EX294) ist eine praktische Ansible-Prüfung auf RHEL und passt gut zu AlmaLinux.
