Ansible code: how it works

How the playbooks and roles in this repository fit together – for anyone who wants to understand, change or extend the code. Day-to-day operation is covered in the operations guides (WordPress, Nextcloud).

Overview

Ansible is a push tool: one machine (the controller) connects to the servers over SSH and carries out, step by step, what the playbooks describe. No agent runs on the servers; all they need is SSH and Python. The description is declarative: a task does not say "install package X" but "package X must be present" – if it already is, nothing happens.

Controller (ansible-playbook, repo, vault password) │ SSH as root, port 10022 (host key is checked) ├──► Blog server blog.yml / blog-update.yml └──► Nextcloud server nextcloud-k3s.yml / nextcloud-update.yml │ └─ on every server: host services (nftables, SSH, fail2ban, monitoring …) + K3s running the applications as Kubernetes workloads

The repository manages two kinds of servers, both AlmaLinux 9 with a single-node K3s cluster:

  • Blog (group blog): WordPress, MariaDB and Redis run entirely in K3s.
  • Nextcloud (group nextcloud): Nextcloud, Collabora and notify_push run in K3s, MariaDB and Redis as services on the host.

Everything shared – hardening, firewall, monitoring, K3s itself – lives in roles prefixed common_ and is used by both playbooks.

Inventory & variables

The inventory (inventory/hosts.yml) assigns each server to a group. The playbooks target a group (hosts: blog); --limit <host> picks one server from it.

Variables come from several places. If a variable is set in more than one, the higher precedence wins. These levels matter in this repo (low to high):

LevelLocationUsed here for
1roles/<role>/defaults/main.ymla role's defaults, e.g. clamav_profiles
2inventory/group_vars/all/*.ymlsame for all servers: versions, paths, resource defaults
3inventory/host_vars/<host>/*.ymlper server: host names, IPs, passwords, own sizing
4play variables (vars: in the playbook)stack: wordpress or stack: nextcloud – which stack is installed
5register / set_facttask results during the run
6-e on the command linebeats everything – for tests and one-offs
Example nextcloud_fpm_mem_limit: "4Gi" is set in group_vars/all/main.yml. A server with more RAM sets a higher value in its host_vars/<host>/vars.yml – that one wins, because host_vars ranks higher. All other servers keep the default.

The full precedence order has more than 20 levels (Ansible docs: "Variable precedence"). In practice the table above is enough; most hard-to-explain effects come from the same variable being set in two places unexpectedly.

Vault

vault.yml is encrypted with ansible-vault. Ansible decrypts it during the run with the vault password (--ask-vault-pass or a .vault_pass file, which never goes into the repo). To edit: ansible-vault edit inventory/host_vars/<host>/vault.yml.

Inputs are validated

Every role that needs values from host_vars describes them in meta/argument_specs.yml – type, description, required or not, and no_log for secrets. Ansible checks this when the role starts: if, say, a vault entry is missing, the run stops at once with the variable's name instead of halfway through the installation. "Required" is only what every server running the role actually has – shared roles such as common_grafana read blog_hostname on the blog and nextcloud_hostname on Nextcloud.

Good to know These checks carry the tag always: they run for all roles even with --tags …. They are fast and read-only.

Versions in one place

inventory/group_vars/all/versions.yml holds every version that gets installed or deployed: K3s, Helm, the Helm charts, all container images, WP-CLI (with checksum), the monitoring binaries and the MariaDB repository series of the Nextcloud servers. The values are listed compactly at the top, the reasons and history per entry below.

  • Always exact, never latest or a floating tag: K3s pulls with IfNotPresent – a floating tag silently stays on whatever build happens to be cached.
  • Not in that file: the Ansible collections (requirements.yml, where ansible-galaxy reads them) and the versions of the checking tools (pre-commit, GitHub Action).
  • Renovate proposes bumps of these lines as pull requests (see tooling).

The playbooks

blog.yml and nextcloud-k3s.yml

Both consist of one play with a list of roles. The order is deliberate:

  1. common_version_check – shows installed and available versions first.
  2. Packages, SSH, firewall, sysctl, CIS hardening – the base, before anything listens.
  3. common_selinux before the deploy – the HostPath directories need their SELinux label before a container uses them.
  4. common_k3s (common_calico now only removes Calico), then the application deploy (blog_k3s_deploy or next_k3s_deploy). The pods start in the background.
  5. Monitoring, fail2ban, mail, automatic updates, rkhunter, ClamAV, auditd, Monit – run while the pods come up (saves minutes).
  6. Configuration inside the application (blog_wordpress or next_config, via kubectl exec) – by now the pods are ready.
  7. *_verify – smoke tests with a coloured report and an e-mail.
  8. common_version_active – is every pin from versions.yml really running? Reports only what is not active yet.
  9. common_aide_refresh always last – refreshes the AIDE baseline so the nightly check does not report the run's own, intended changes as an alarm.

Every role has a tag with its name. --tags common_k3s,blog_k3s_deploy runs just those roles. The formerly separate roles carry their own name as tag too: common_clamav and common_selinux (until October 2026 blog_clamav, next_selinux …).

The update playbooks

blog-update.yml and nextcloud-update.yml are for updates while running and do not touch the host. Both require --limit; Nextcloud uses serial: 1, one server after the other, and stops at the first failure.

Pre-flight (outside the block) healthy? otherwise stop, nothing is touched block: pull the Deployments' images again, compare digests with the running pods restart only Deployments with a rebuilt image (role common_image_refresh) Blog: run the nightly update job now (DB dump first), evaluate it Nextcloud: occ upgrade, occ app:update --all, second restart for OPcache post-check (Nextcloud: no maintenance mode, no pending DB upgrade) rescue: collect the state (occ status, pods, events, nextcloud.log / newest DB dump) Nextcloud: switch maintenance mode off only if the upgrade itself has completed stop clearly – no further server

Roles

A role is a self-contained task with a fixed directory layout (see layout). Large roles are split into thematic files that tasks/main.yml pulls in with import_tasks in a fixed order (e.g. blog_wordpress: install, security_muplugin, plugins, appearance, ai_disclosure, media, settings, updates).

Shared roles with a profile

Every full playbook sets a play variable stack (blog.yml: wordpress, nextcloud-k3s.yml: nextcloud). It is the one place that says which stack is being installed. Shared roles ask only this variable – not the inventory group, because the test host is in both groups. Templates decide with {% if stack == 'nextcloud' %} (firewall, Prometheus, Monit, version check); where blog and Nextcloud need the same thing with different values, stack selects a profile:

The roles in detail

Each role in three parts: What it does, Why it exists, and How it works – as a chain of steps with the Ansible building blocks (→ = then). The order is the order of the playbooks. The task-by-task version is the comment at the top of each file under roles/<role>/tasks/.

Preparation and base system

common_version_check (both)

What: At the start of every run, shows which versions of K3s, Helm, nginx-ingress and cert-manager are installed, pinned and newly available. Why: Before each run you see whether a pin in versions.yml is outdated or not rolled out yet.

How: collect the versions (command on the server, uri against the GitHub API) → bring them into one notation with a first set_fact (regex_search, from_json) → compare them with a second set_fact (== yields true/false) → print a coloured report with debug. Read-only, never aborts.

blog_packages / next_packages (per stack)

What: Hostname, package repositories (EPEL; for Nextcloud also CRB and MariaDB), system update, base packages. Why: Without them, every later role lacks tools and dependencies.

How: set the hostname (hostname) → set up repositories (read dnf repolist first, enable only what is missing) → update everything except the kernel (dnf name: "*" state: latest; the kernel cannot be installed from the sandboxed SSH session – ProtectKernelModules from common_ssh – it comes at night via dnf-automatic) → reboot if the running kernel’s module directory is gone (checked via systemd-run, the session itself sees it empty); only the blog also checks needs-restarting -r – on Nextcloud such reboots come at night via dnf-automatic → install packages → stop and mask unused services.

common_ssh (both)

What: SSH on port 10022, hardened sshd_config (keys only), SELinux label for the port, mail alarm on every interactive login. Why: Takes away the basis for automated attacks on port 22 and rules out password logins. A systemd drop-in also puts a sandbox around sshd that every SSH session inherits: no kernel modules, no kernel tunables – that only works deliberately via systemd-run (details in the operations docs, "Important security notes").

How: remember whether this is the first run (set_fact ssh_first_run) → read the SELinux port list, set the label only if needed → copy configuration and drop-ins (copy, notify) → handler chain at the end: check with sshd -t → restart sshd (async, because the own connection drops) → reset_connection → wait_for_connection → finally set up the login alarm: script from a template, a systemd timer every 2 minutes that mails new interactive logins from wtmp.

common_firewall (both)

What: nftables rules for IPv4/IPv6, optionally a country filter for SSH. Why: Only what is explicitly allowed gets through; fail2ban gets its ban sets.

How: detect DHCP or static (read nmcli → set_fact) → optionally build the country list → write the ruleset from the template, checked first (template validate: nft -c) → limit reloads to the own table (systemd drop-in) → the handler reloads nftables and lets fail2ban re-add its bans (listen). First run: reboot instead of live activation (include_tasks … when).

common_sysctl (both)

What: Kernel parameters (TCP BBR, timeouts, queues, CIS network hardening) and Transparent Huge Pages set to madvise. Why: Faster web server, known network weaknesses closed.

How: load the tcp_bbr module and register it for boot → values as files in /etc/sysctl.d/ (template, persistent) → apply immediately (sysctl --system via systemd-run, because the sandboxed SSH session may not write kernel values) → a small systemd unit sets THP on every boot.

common_cis_hardening (both)

What: The CIS benchmark items that are safe to apply: AIDE, blocked kernel modules, journal, no core dumps, cron/sudo permissions, mount options. Why: Less attack surface; risky items (PAM, GRUB, crypto policy) are deliberately left out.

How: a series of small, independent groups, each following "check the state → change only if needed": e.g. create the AIDE database only if it is missing (stat → when) → write sudoers only after checking it (validate: visudo -cf) → write mount options to fstab and activate them right away (mount state: mounted).

common_selinux (both, profile via stack)

What: SELinux in enforcing mode and the host directories that are mounted into the pods as storage. Why: Containers may only write to files of type container_file_t.

How: pick the profile (selinux_profiles[stack]) → create directories with owner and mode (file, loop) → register the rule persistently (semanage fcontext; "already defined" counts neither as an error nor as a change) → apply it to existing files (restorecon).

Nextcloud only: database and cache on the host

next_mariadb (Nextcloud)

What: MariaDB on the host: systemd hardening, slow query log, rotation, database, user. Why: Nextcloud needs a database that only the pods can reach.

How: check whether the Nextcloud database already exists (register db_check) → first run only: create root password, database and user (when: db_check.rc != 0) → every run: remove anonymous accounts and the test database, create or correct the exporter user (community.mysql, idempotent, no_log).

next_redis (Nextcloud)

What: Make Redis reachable for the pods and protect it with a password. Why: Redis holds Nextcloud's file locks and sessions.

How: check that the password is in the vault (assert) → set three lines in redis.conf (lineinfile, notify) → restart right away instead of at the end (meta: flush_handlers) → wait until the port answers (wait_for).

Kubernetes and the application

common_k3s (both)

What: K3s, Helm with the helm-diff plugin, cert-manager (Let's Encrypt) and the F5 nginx ingress. The bundled K3s components nobody needs here (Traefik, ServiceLB, local-storage) are switched off. Why: This is the platform the blog and Nextcloud run on. What does not run cannot be attacked.

How: read the installed version (register) → download the binary only if it differs from k3s_version (get_url force: true … when, notify) → restart right away (flush_handlers) → wait until the API answers (until) → Helm the same way → download helm-diff only if the version differs from helm_diff_version (checksum in get_url) → install the charts (kubernetes.core.helm only changes something on a different chart version or different values).

common_calico (both)

What: Since 2026-10-19 it removes Calico: the cluster objects (same template, state: absent) and what Felix leaves on the host (files/calico-cleanup.sh). Why: Calico ran in policy-only mode to enforce the NetworkPolicies, but Felix only matches pod interfaces named cali* and K3s's Flannel creates veth* – it never enforced anything. The policies are enforced by K3s's built-in controller (kube-router), tested with a pod from another namespace.

How: the K8s apply pattern (now explained in common_k3s, used by 26 tasks) with state: absent → wait until no calico-node pod is left (k8s_info + until) → the cleanup script removes only Calico's rules, chains, ipsets and the calico-arp table and prints a line per object, which changed_when reads.

common_kube_metrics (both)

What: A ServiceAccount that may only read the kubelet's metrics, plus kube-state-metrics in kube-system (NodePort 30808, local only). Why: Node Exporter sees the host as a whole; this shows CPU, memory, throttling, restarts and OOM kills per container against its limits (Grafana dashboard "Container-Ressourcen", four alerts).

How: K8s apply pattern → common_prometheus reads the account's token Secret (k8s_info, retried until the token controller has filled it) and writes it to /etc/prometheus/kubelet-token for the kubelet_cadvisor job.

blog_k3s_deploy / next_k3s_deploy (per stack)

What: All Kubernetes objects of the application: namespace, secrets, ConfigMaps, deployments, services, ingress, CronJobs, NetworkPolicies, image policy (for Nextcloud also Collabora, notify_push, app reconciliation). Why: So the application can be rebuilt from the repo at any time.

How: one template and one task file per component, in dependency order (import_tasks) → apply each with the K8s apply pattern → wait for the new pods only if something changed → Nextcloud: MariaDB/Redis on the host as "external services" (service without selector + endpoints pointing at the host IP).

Monitoring

common_node_exporter / common_mysqld_exporter (both / Nextcloud only)

What: Expose metrics of the host and of the host MariaDB locally (127.0.0.1:9100 / :9104). Why: Prometheus scrapes them there; nothing is reachable from outside.

How: read the installed version → download, unpack and install the archive only on a different version (get_url → unarchive → copy, skipped in check mode) → write the systemd unit + sandbox drop-in (notify) → handlers reload systemd and restart the service once. The MariaDB exporter reads its password from a file only it can read (no_log).

common_prometheus (both)

What: Collects the metrics of all exporters and keeps them for 30 days, reachable only locally. Why: Basis for Grafana graphs and alerts.

How: as with the exporters (check the version → download only on a difference) → configuration from the template, which adds the right exporters per stack (template) → unit and sandbox → exactly one restart at the end, no matter how many files changed (handler).

common_grafana (both)

What: Grafana with a Prometheus data source, four dashboards and alert mails, reachable at /grafana/. Why: Graphs and warnings without Prometheus itself having to face the outside.

How: install the package, set single lines in grafana.ini (lineinfile) → start and wait until the API answers (uri … until) → via the HTTP API "look first, then create" (register the GET → POST only when it is missing) → download and import dashboards → alert rules via a small Python script.

Protection, mail and maintenance

common_fail2ban (both)

What: Bans IP addresses that attack SSH or the logins or probe the system. Why: Automated attacks end after a few attempts instead of never.

How: own ban action (writes into the firewall's nftables sets), five filters and jail.local with seven jails from templates (template, notify) → start the service → a timer reloads the HTTP jails as soon as the ingress pod creates a new log file.

common_msmtp (both)

What: msmtp as a lean replacement for sendmail. Why: cron, rkhunter, ClamAV, dnf-automatic and the check reports can send mail.

How: install the package → /etc/msmtprc from the template (relay, port, credentials from the vault; mode 0600) → create the log file once (file state: touch with preserve, so it does not count as changed every time). No service: every program starts msmtp itself.

common_dnf_automatic (both)

What: Installs security updates at night and reboots at 03:30 if needed. Why: Vulnerabilities get closed without anyone having to remember.

How: two lines in automatic.conf (security updates only, really install) → move the timer to 01:00 with a drop-in (restarted only if the drop-in changed: register → is changed) → two cron entries: reboot if needed and a check mail at 06:00.

common_rkhunter (both)

What: Looks for rootkits and changed system files at night, mails only on findings. Why: Early warning in case the server has been compromised.

How: set options (lineinfile in a loop over key/value) → build the reference database (--propupd) → create the nightly cron entry, remove the package's duplicate scan → dnf plugin that renews the database after every update (otherwise false alarm).

common_clamav (both, profile via stack)

What: Nightly virus scan of uploaded files (blog: uploads, Nextcloud: user data), mail only on findings. Why: Malware in someone else's uploads is noticed by the next morning at the latest.

How: pick the profile (set_fact clamav: clamav_profiles[stack]) → download signatures once (creates:), after that the freshclam service keeps them current → generate exclude patterns for media files with Jinja → write the scan script (copy with a Jinja {% if %}) → cron entry.

blog_visitor_stats (blog)

What: Every night, anonymously counts the previous day's visitors from the ingress log and stores only numbers. Why: Trends over months, although K3s keeps the logs only for a few days – no IP leaves the server.

How: copy the script and the country database updater → two systemd timers from templates (flush_handlers before starting) → once: download the country database and backfill the days still available (creates:, loop over 1–5 days).

common_auditd (both)

What: The kernel logs security-relevant events (user files, sudo, SSH configuration, K3s keys …). Why: Traces for later investigation, and a mail on events that should never happen.

How: copy the rules file → the handler loads it into the kernel (augenrules --load) → report script and a cron job every ten minutes that mails only the critical keys.

common_logrotate (both)

What: Rotation rules for logs that have none or incomplete ones (Grafana, Prometheus, fail2ban, rkhunter). Why: Otherwise they grow without limit.

How: four copy tasks into /etc/logrotate.d/ – no restart needed, logrotate reads them on its next daily run.

common_monit (both)

What: Watchdog for services, firewall, pods, certificates, storage and backups; restarts fail2ban if it fails. Why: Mails only on state changes – so every mail means something.

How: check that the mail credentials are there (assert) → find out which services exist on this host (systemctl cat in a loop → zip + selectattr) → check scripts and configuration from templates → check the configuration with monit -t → start.

Configuring and checking the application

blog_wordpress (blog)

What: WordPress in the running pod via WP-CLI: installation, hardening plugin, plugins, menu/CSS, AI notice, uploads as WebP below 280 KB (since 2026-10-19), settings, updates. Why: The blog's setup is reproducible, and updates come along with every run.

How: everywhere "read the state → change only what is needed": e.g. read the plugin list once (from_json) → install only missing ones (difference), activate only inactive ones (selectattr) → write PHP files as .new first, swap them only on a different checksum → compare versions before and after the updates, restart only then.

next_config (Nextcloud)

What: Nextcloud in the running pod via occ: domains, URL, mail, database maintenance, office and preview apps, Collabora connection, password policy. Why: The settings live in the repo instead of only in the running instance.

How: for every value "get → compare → set": read the current value (occ config:…:get, register) → write only when it differs (changed_when: true) → so an unchanged run reports nothing, and a value changed by hand is reset and shown as a change. As the last step the same chain for the password policy (password_policy.yml): enable the app → read the values → delete differing old values → set them again with a type (--type=integer|boolean).

blog_verify / nextcloud_verify (per stack)

What: Smoke tests after the run: services, pods, HTTPS, certificate, headers, blocked paths, database/cache. Why: A run that reports "ok" does not mean the site works.

How: only collect all checks (register _v_*, failed_when: false) → convert to true/false with set_fact (_r_*) → count, print the report, send the mail → only at the very end assert the critical points. Same pattern as the version check: gather first, then prepare, then judge.

common_version_active (both)

What: The counterpart of the version check at the end: compares every pin in versions.yml with what is running – the kubelet version, the deployed charts, the images of running containers, Prometheus/exporter build info, a pending reboot and services still on replaced code. Why: Installed is not active: a new binary needs a restart, a new image new pods, a new kernel a reboot (found 2026-10-19: a K3s bump had silently never been installed).

How: read-only queries (command, uri, check_mode: false) → parse the JSON in Jinja (from_json, selectattr, map) → collect one row per component with loop + set_fact → print only the rows that do not match. Never fails the play.

common_aide_refresh (both)

What: As the last role, renews the AIDE reference database if the run changed watched files. Why: Otherwise AIDE reports the run's own changes as a finding the next night.

How: a single scan compares and writes the new database (aide --update) → evaluate the return code (1–7 = differences, 0 = identical, 14 and up = error) → activate the new database only on differences – the only task that reports "changed".

Helper roles (not directly in the playbook)

common_verify – The shared checks for host, Kubernetes and HTTP. How: included by the verify roles with import_role … tasks_from, only collects results (_v_*); the calling role makes the judgement.

common_image_refresh – For the update playbooks: which deployments have a freshly built image? How: a Python script (script) pulls each image again and compares the digest with the running pod → result as JSON → set_fact → only what was really rebuilt gets restarted.

What happens during a run

  1. Gather facts – only gather_subset: min; nothing more is used anywhere.
  2. Per role: first the argument validation, then the tasks in order. Each task reports ok (nothing to do), changed (changed something), skipped (condition not met) or failed.
  3. Handlers: a task with notify: Reload nftables only queues the handler when it reports changed. Handlers run together at the end of the play – or earlier where a role uses meta: flush_handlers (e.g. K3s must be restarted before the play continues). Several handlers can react to the same event via listen: (reload nftables, then let fail2ban re-apply its bans).
  4. Summary (PLAY RECAP) with ok/changed/failed per server, plus the time per task.

Dry run: --check --diff

With --check Ansible changes nothing and reports what it would change; --diff shows the differences. To make that meaningful here:

  • Pure queries (versions, occ config:system:get, kubectl get, systemctl is-active) have check_mode: false and run in the dry run too – otherwise later tasks would have no data.
  • Writing commands are skipped. Where that would hide a pending change, a dedicated task reports it (e.g. "mail_smtphost would be updated").
  • The k8s module compares Kubernetes objects with the cluster via a server-side dry run – the diff shows exactly the fields that change.

Kubernetes from Ansible

The applications are Kubernetes objects. Ansible renders them from Jinja2 templates and hands them straight to the K3s API with the kubernetes.core.k8s module:

- name: Redis | Apply Deployment + Service
  kubernetes.core.k8s:
    kubeconfig: "{{ k3s_kubeconfig }}"
    state: present
    apply: true
    definition: "{{ item }}"
  loop: "{{ k8s_objects if ansible_diff_mode else [k8s_objects] }}"
  loop_control:
    label: "{{ (item.kind ~ '/' ~ item.metadata.name) if item is mapping else ((item | length) ~ ' objects') }}"
  vars:
    k8s_objects: "{{ lookup('ansible.builtin.template', 'redis-deployment.yml.j2') | ansible.builtin.from_yaml_all | select | list }}"
  register: redis_apply
  • lookup('template', …) renders the template in memory; from_yaml_all splits it into the single objects. Nothing ends up in /tmp – no Secrets either.
  • apply: true behaves like kubectl apply (via the last-applied-configuration annotation), so it is compatible with the existing objects.
  • One call or one per object: on normal runs all objects of a template go to the API in one call (the former Calico manifest with 34 objects: under 2 instead of ~30 seconds). Only with --diff (i.e. in check-drift.sh) does the loop run per object – only then does the diff show each object's change, and the output names Deployment/redis, Service/redis.
  • The module only reports changed when the object really changes. Follow-up tasks such as "wait for the rollout" depend on redis_apply.changed.
  • Queries use kubernetes.core.k8s_info (does the Secret exist yet?).
  • The Helm charts (cert-manager, nginx-ingress) are managed by kubernetes.core.helm: it compares chart version and values of the running release and only upgrades on a difference. With the helm-diff plugin, --check --diff also shows which chart values would change.
  • Needed on the server: the python3-kubernetes package (installed by common_k3s); on the controller: the kubernetes.core collection ≥ 6.5.0 (Helm 4).

What happens inside the containers – occ for Nextcloud, wp-cli for WordPress (always as www-data) – still runs via k3s kubectl exec.

Idempotency & "changed"

Idempotent means: the second run in a row changes nothing and reports changed=0 everywhere. Only then does a changed mean something – and a dry run reliably shows what a real run would do. The patterns in this code:

PatternExample
module instead of a commandansible.builtin.dnf, file, template, kubernetes.core.k8s know themselves whether there is anything to do
creates:freshclam only while /var/lib/clamav/freshclam.dat is missing
changed_when from the outputocc upgrade is only "changed" when it says "Update successful"
read – compare – writeNextcloud's nine mail settings: config:system:get first, set only what differs; the exporter DB user: check password hash and grants first
changed_when: falseonly for real queries – never for a command that writes
The trap A command task that writes every time and has changed_when: false looks harmless but hides every change. A task that reports changed every time turns every run into "drift". Both are gone here; scripts/check-drift.sh shows at once if one comes back.

Error handling

  • ansible.builtin.assert checks preconditions and stops with an understandable message (update without --limit, Nextcloud not healthy, exporter password missing from the vault).
  • failed_when defines what counts as a failure – e.g. "already installed" from occ app:install is not one.
  • block/rescue in the update playbooks: if a step in the block fails, the rescue part runs. It can read ansible_failed_task and ansible_failed_result and prints task name, error message and output.
  • The pre-flight check sits outside the block on purpose: the rescue must only deal with states the run itself caused. If Nextcloud is already in maintenance mode beforehand, the playbook refuses instead of "cleaning it up".

Secrets

  • Passwords live only in vault.yml (encrypted, gitignored).
  • no_log: true on every task that handles them – also on k8s_info queries of Secrets, because the result contains the data. In loops, no_log can apply per item (no_log: "{{ item.secret | default(false) }}").
  • Argument specs mark vault values with no_log – tested: they show up neither with -vvv nor in an error message.
  • Kubernetes Secrets are rendered in memory and handed to the API, never written to a file on the server.
  • Values for occ go via argv, not through a shell line – a quote in a password cannot change the command.
  • Before every commit, gitleaks looks for keys and tokens (see next section).

Tests

tests/k8s/run.sh – the Kubernetes roles without a server

Starts K3s (same version as k3s_version) as a bare API server in podman, applies the manifests first with the roles from main (the servers' state), then with the working tree: dry run, real run, second real run, dry run. Fails if the second run still changes something, a pod would be rolled out again, a Helm release gets a new revision – or if a deliberately changed image version is not detected. No pods run: what happens inside the containers (occ, wp-cli) is not part of this test.

tests/update/run.sh – failure cases of the update playbooks

14 scenarios against stand-ins for kubectl/crictl: healthy, rebuilt image, maintenance mode already on, upgrade aborts, failure after a completed upgrade, rollout hangs, update job fails, blog not running, dry run. Checked: exit code, the commands that ran, and the maintenance mode afterwards.

scripts/check-drift.sh – against a real server

scripts/check-drift.sh nextcloud-k3s.yml <host> --ask-vault-pass
scripts/check-drift.sh blog.yml <host> --tags blog_k3s_deploy --ask-vault-pass

A dry run with --check --diff; it prints only the tasks that would change something, with a readable diff (Kubernetes bookkeeping fields hidden). Exit code 0 = no drift. Right after a real run it must say "NO DRIFT" – otherwise a task is not idempotent.

Workflow for a change

  1. Change it – role, template or versions.yml.
  2. ansible-lint (runs on commit anyway).
  3. Kubernetes roles touched: tests/k8s/run.sh; an update playbook touched: tests/update/run.sh.
  4. scripts/check-drift.sh <playbook> <host> – shows what the real run will change. Does that match the intent?
  5. Real run, on one server first, limited with --tags to what is needed.
  6. check-drift.sh once more → "NO DRIFT".
  7. Commit (the hooks check lint and secrets), push.
Version update Read the Renovate PR (or your own change in versions.yml) → check the component's release notes → check-drift.sh → roll out with the matching tag (e.g. --tags common_k3s,blog_k3s_deploy) → merge.

Pitfalls

  • Same variable in two places – check precedence (ansible -m debug -a var=… against the host shows the value that actually applies).
  • item in nested loops – an outer loop around include_role needs loop_control: loop_var: …, otherwise the role's own loops overwrite item.
  • Loop and when – the loop is evaluated before the condition; a template in loop: must render even when when is false.
  • Tags and include_role – tags are inherited only by import_* (static), not by include_* (dynamic).
  • /tmp is noexec (CIS) – call scripts there with sh script, do not execute them directly.
  • Module names with collection – ansible.builtin.ini_file only "worked" through a redirect to community.general. ansible-lint finds this (syntax-check[unknown-module]).
  • Cron entries are identified by their name – change the name and you get two entries.

Learning path

  1. Read with a goal: pick a role (e.g. common_clamav) and explain for every task why it looks the way it does – module, condition, changed_when.
  2. Experience idempotency: run a role twice via --tags; the second run must show changed=0; then check-drift.sh.
  3. Write a role yourself – without a template, with argument_specs, a handler and a test; then compare it with an existing one.
  4. Tools: ansible-doc <module>, ansible <host> -m setup, --start-at-task, --step, -vvv.
  5. A structured goal: the RHCE exam (EX294) is a hands-on Ansible exam on RHEL and fits AlmaLinux well.
