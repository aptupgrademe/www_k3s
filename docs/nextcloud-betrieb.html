Nextcloud – Betriebs­dokumentation

Nextcloud 34 auf K3s (AlmaLinux 9) · Letzte Aktualisierung: Juli 2026

Überblick

Nextcloud läuft auf einem Single-Node-K3s-Cluster auf AlmaLinux 9. Die gesamte Infrastruktur wird mit einem Ansible-Playbook (nextcloud-k3s.yml) aufgebaut und verwaltet. Das Playbook ist idempotent – es kann jederzeit neu ausgeführt werden, ohne Daten zu verändern oder Dienste unnötig zu unterbrechen.

Design-Entscheidung: Single-Node Der Server läuft als einzelner Kubernetes-Node. Es gibt keine Hochverfügbarkeit. Updates und Neustarts verursachen eine kurze Ausfallzeit (typisch: 30–60 Sekunden). Die Recreate-Strategie im Deployment stellt sicher, dass immer nur ein Pod auf die HostPath-Volumes zugreift.

Nextcloud-Pod im Detail

Beide Container teilen sich denselben Pod (= dasselbe Netzwerk-Namespace und die gleichen Volumes). Dadurch kann nginx via 127.0.0.1:9000 mit PHP-FPM kommunizieren, ohne einen Kubernetes-Service zu benötigen.

Init-Container: init-dirs

Läuft einmalig vor dem Start der Hauptcontainer. Setzt die Ownership der HostPath-Verzeichnisse auf UID 33 (www-data im Container) und setzt die Berechtigungen. Ohne diesen Schritt kann Nextcloud nichts in /var/www/html schreiben.

Container 1: nextcloud-fpm

Das offizielle nextcloud:34-fpm-Image. Führt PHP-FPM auf Port 9000 aus. Bei einem leeren /var/www/html installiert der Docker-Entrypoint Nextcloud automatisch anhand der Umgebungsvariablen (DB, Admin, Redis). Bei einem Update läuft occ upgrade automatisch.

Container 2: nginx

nginx-Sidecar (nginx:1.31-alpine) auf Port 80. Beantwortet statische Anfragen direkt aus dem gemeinsamen Volume; PHP-Anfragen werden per FastCGI an Port 9000 weitergeleitet. TLS ist bereits durch nginx-ingress (F5) terminiert – nginx spricht nur plain HTTP.

Speicher & Daten

Wichtig: Alle Verzeichnisse liegen auf derselben Partition /dev/vda4 (119 GB). Es gibt keine getrennten Volumes für App und Daten.
Pfad auf dem HostMountpoint im ContainerInhaltBesitzer
/srv/nextcloud-www /var/www/html PHP-App, Apps, Themes, config/ root:root 755 (Verz.)
33:33 für config/

/var/lib/mysql – MariaDB-Datenbank (läuft direkt auf dem Host) mysql:mysql

Warum sind App und Daten getrennt?

Nextcloud-App-Dateien (/srv/nextcloud-www) und Benutzerdaten (/data) sind bewusst in zwei separate HostPath-Volumes aufgeteilt, weil:

  • Benutzerdaten können unabhängig gesichert werden (täglich empfohlen)
  • App-Dateien werden bei einem Update durch das neue Image ersetzt
  • Bei einer Neu-Installation genügt ein leeres /srv/nextcloud-www – Nextcloud installiert sich selbst beim ersten Start

Wichtige Konfigurationsdatei: config.php

Nextcloud liest alle *.php-Dateien aus /var/www/html/config/ automatisch. Es gibt zwei Quellen:

  • config.php – von Nextcloud selbst geschrieben (Erstinstallation)
  • custom.config.php – aus dem Kubernetes-ConfigMap nextcloud-custom-config, verwaltet durch Ansible. Diese Datei hat Vorrang und überschreibt Werte aus config.php.
Ownership-Falle beim ConfigMap-Mount Kubernetes erstellt beim Mount eines ConfigMap-subPath das Elternverzeichnis ggf. als root:root. Deshalb muss /srv/nextcloud-www/config/ vorab mit owner: 33 angelegt werden (Ansible-Task next_k3s_deploy/tasks/dirs.yml).

Benötigte DNS-Einträge

Vor dem ersten Playbook-Lauf müssen die DNS-Einträge beim Domain-Registrar angelegt sein. cert-manager benötigt sie für den Let's Encrypt HTTP-01-Challenge – ohne gültige Einträge schlägt die Zertifikatsausstellung fehl.

Name (Hostname)TypWertZweck
nextcloud.example.de A Öffentliche IP des Servers Nextcloud-Weboberfläche, Let's Encrypt TLS
collabora.example.de A Öffentliche IP des Servers Collabora CODE Online (Office-Bearbeitung), eigenes TLS-Zertifikat
Collabora braucht einen eigenen Hostnamen Collabora läuft als separater Ingress auf einem eigenen Subdomain-Namen. Wird nur ein A-Record angelegt (ohne Collabora), kann der WOPI-Callback von Nextcloud zu Collabora nicht funktionieren und Dokumente lassen sich nicht online bearbeiten.
IPv6 (optional) Falls der Server eine öffentliche IPv6-Adresse hat, können zusätzlich AAAA-Records für beide Hostnamen angelegt werden. Die Firewall-Regeln (/etc/nftables.conf) sind bereits konfiguriert.

Wie Pods den Host erreichen (MariaDB / Redis)

MariaDB und Redis laufen als Host-Dienste. Pods verbinden sich darüber via K8s ExternalServices: ein Service ohne Selector mit manuell gepflegten Endpoints, die auf die öffentliche IP des Hosts zeigen. 

Pod → mariadb.nextcloud.svc.cluster.local (10.43.x.x)
   → Endpoint: 82.165.165.230:3306
   → nftables accept für 10.42.0.0/16 auf :3306

Der MariaDB-Datenbanknutzer ist auf den Pod-CIDR eingeschränkt ('nextcloud'@'10.42.%'). Eine direkte Verbindung vom Host funktioniert nur als root via Unix-Socket.

TLS und Proxy-Kette

Internet
  → nginx-ingress (F5) (Port 443, TLS terminiert, setzt X-Forwarded-For / -Proto)
    → nginx-Sidecar (Port 80, plain HTTP)
      → PHP-FPM (Port 9000, FastCGI)
        fastcgi_param HTTPS on
        fastcgi_param HTTP_SCHEME https

Nextcloud muss wissen, dass Anfragen über einen Proxy kommen: 

'trusted_proxies'       => ['10.42.0.0/16'],
'forwarded_for_headers' => ['HTTP_X_FORWARDED_FOR'],
'overwriteprotocol'     => 'https',
Wichtig: trusted_proxies muss den Pod-CIDR enthalten Fehlt dieser Eintrag, zeigt Nextcloud im Admin-Panel die Warnung "Konfiguration des Reverse-Proxy-Headers ist falsch". nginx-ingress (F5) leitet Anfragen mit seiner Pod-IP (10.42.x.x) weiter – diese muss als vertrauenswürdiger Proxy eingetragen sein.

WOPI (Collabora)

Collabora ruft für die Dokument-Bearbeitung Nextclouds WOPI-API auf. Diese Rückrufe kommen von der Pod-IP des Collabora-Pods (10.42.x.x) – nicht von der Service-IP. Die wopi_allowlist muss daher den Pod-CIDR enthalten: 

# inventory/host_vars/<host>/vars.yml
wopi_allowed_hosts:
  - "10.42.0.0/16"   # Pod-CIDR (Collabora-Pod → Nextcloud WOPI)
  - "10.43.0.0/16"   # Service-CIDR
  - "collabora.inspired-as-code.de"

NetworkPolicy (Calico)

K3s's Standard-CNI (Flannel) setzt Kubernetes-NetworkPolicy-Objekte überhaupt nicht durch – sie können im Cluster existieren, ohne irgendeine Wirkung zu haben (live verifiziert: eine Deny-All-Policy hat nichts verändert, bis Calico installiert wurde). Die Rolle common_calico installiert Calico im Policy-Only-Modus: es laufen nur Felix (die Policy-Engine) und kube-controllers, die Pods und NetworkPolicy-Objekte direkt über die Kubernetes-API lesen. Flannel übernimmt weiterhin unverändert das gesamte Pod-Networking, die IP-Vergabe und den CNI-Plugin-Aufruf – Calico ergänzt nur die Durchsetzung obendrauf.

next_k3s_deploy wendet eine Policy an, collabora-netpol, die den Collabora-Pod einschränkt: anders als nextcloud-fpm hat Collabora keinen legitimen Grund, jemals direkt auf MariaDB oder Redis zuzugreifen – sein Egress ist daher auf DNS, den Nextcloud-Pod (WOPI, Port 80/443) und sonst nichts beschränkt. Ingress ist auf nginx-ingress (Host-IP) und den Nextcloud-Pod beschränkt. 

# Prüfen, ob die Policy vorhanden ist, und Calicos Pods ansehen
kubectl get networkpolicy -n nextcloud
kubectl get pods -n kube-system -l 'k8s-app in (calico-node,calico-kube-controllers)'

# Durchsetzung tatsächlich nachweisen (temporäre Testpolicy)
kubectl exec -n nextcloud deployment/collabora -- nc -z -w4 <mariadb-host-ip> 3306
# → sollte fehlschlagen/Timeout; klappt es doch, setzt Calico nicht durch
Nur Nextcloud ist abgedeckt, WordPress nicht Das ist Absicht: WordPress' realistischer Kompromittierungsweg (eine verwundbare Plugin-Lücke innerhalb von wordpress-fpm) braucht ohnehin schon legitimen direkten DB-Zugriff – eine NetworkPolicy würde das dort nicht verhindern. Collaboras Bedrohungsmodell ist anders: es verarbeitet beliebige hochgeladene Dokumente und hat keinen legitimen DB-/Redis-Zugriff zu verlieren – die Einschränkung ist also ein echter, durchsetzbarer Sicherheitsgewinn und keine Show-Maßnahme.
Neuen Pod/Service im Namespace nextcloud hinzugefügt? Nur der Collabora-Pod ist eingeschränkt; alles andere im Namespace bleibt weiterhin standardmäßig erlaubt. Wird eine NetworkPolicy für einen weiteren Pod ergänzt: Calico setzt pro Pod-Label-Selector durch, nicht nach Pod-Name – unbedingt prüfen, ob der podSelector passt, bevor man annimmt, eine Policy greife.

Variablen & Secrets

Wo Credentials liegen

Alle Passwörter stehen in inventory/host_vars/<host>/vault.yml, verschlüsselt mit Ansible Vault. Diese Datei darf niemals unverschlüsselt in git committed werden. 

# Verschlüsseln vor dem Commit:
ansible-vault encrypt inventory/host_vars/test/vault.yml

# Entschlüsseln zum Bearbeiten:
ansible-vault decrypt inventory/host_vars/test/vault.yml
# (danach sofort wieder verschlüsseln!)

# Direkt im Editor öffnen (bevorzugt):
ansible-vault edit inventory/host_vars/test/vault.yml

Passwort-Eintrag für unbeaufsichtigte Runs

# .vault_pass (niemals committen – steht in .gitignore)
echo "mein-vault-passwort" > .vault_pass
# In ansible.cfg einkommentieren:
# vault_password_file = .vault_pass

Die Vault-Variablen fließen beim Playbook-Run in das K8s-Secret nextcloud-secrets im Namespace nextcloud. Das Secret wird als Umgebungsvariablen in den Pod injiziert.

Container-Images & Versionen

Alle Image-Tags sind in inventory/group_vars/all.yml zentral definiert. Da imagePullPolicy standardmäßig IfNotPresent für getaggte Images ist, zieht K3s automatisch ein neues Image nur dann, wenn der Tag im Manifest geändert wurde. 

# inventory/group_vars/all.yml
nextcloud_image_fpm:       "nextcloud:34-fpm"      # Nextcloud PHP-FPM
nextcloud_image_nginx:     "nginx:1.31-alpine"          # nginx Sidecar
nextcloud_image_collabora: "collabora/code:26.04.1.4.1" # Collabora CODE
nextcloud_image_busybox:   "busybox:1"             # Init-Container

Tag-Strategie

Tag-FormatBedeutungBeispiel
34-fpm Folgt Minor- und Patch-Updates in Nextcloud 34.x automatisch beim Pull nextcloud:34-fpm (aktuell)
35-fpm Nächste Major-Version – muss explizit gesetzt werden Änderung in all.yml nötig
1.31-alpine nginx Minor-Track; Patch-Updates kommen automatisch nginx:1.31-alpine (aktuell)
26.04 Collabora Release-Cycle (quartalsweise) collabora/code:26.04.1.4.1 (aktuell) → 26.08
Patch-Update ohne Tag-Änderung Wenn Docker Hub z.B. nextcloud:34-fpm von 34.0.1 auf 34.0.2 aktualisiert, passiert auf dem Server nichts automatisch. Der Tag ist lokal gecacht. Manuell updaten: 
crictl pull docker.io/library/nextcloud:34-fpm
k3s kubectl rollout restart deployment/nextcloud -n nextcloud

Playbook ausführen

Vollständiger Erstlauf (neue Server-Installation)

  1. SSH-Port auf 22 setzen in inventory/host_vars/test/vars.yml: ansible_port: 22
  2. Vault-Passwörter in vault.yml eintragen und verschlüsseln
  3. Collections installieren: ansible-galaxy collection install -r requirements.yml
  4. Playbook ausführen: 
    ansible-playbook nextcloud-k3s.yml --limit test --ask-vault-pass
  5. SSH-Port in vars.yml auf 10022 ändern (nach SSH-Hardening durch common_ssh)
Deployment-Verification (nextcloud_verify) Am Ende von nextcloud-k3s.yml führt die Rolle nextcloud_verify automatisch 31 Smoke-Tests durch: Dienste, K8s-Pods, HTTPS-Erreichbarkeit, Security-Header, Nextcloud-Status. Fehlschlagende Tests werden als Ansible-Fehler gemeldet.

Idempotente Wiederholung (z.B. nach Konfig-Änderung)

ansible-playbook nextcloud-k3s.yml --limit test --ask-vault-pass

Das Playbook erkennt, was bereits korrekt konfiguriert ist, und ändert nur, was nötig ist. Kubernetes-Manifeste werden nur dann neu gerollt, wenn sich das Manifest geändert hat (changed: "configured" in output).

Nur bestimmte Rollen ausführen

# Nur Nextcloud-Konfiguration (occ-Befehle)
ansible-playbook nextcloud-k3s.yml --limit test --tags next_config --ask-vault-pass

# Nur K8s-Deployments aktualisieren
ansible-playbook nextcloud-k3s.yml --limit test --tags next_k3s_deploy --ask-vault-pass

MariaDB Slow Query Log

Der Host-MariaDB schreibt langsame Queries (≥ 1 Sekunde) nach /var/log/mariadb/slow.log. Die Datei wird von MariaDB automatisch angelegt und kann per journalctl oder direkt gelesen werden. 

# Slow-Query-Log live lesen
tail -f /var/log/mariadb/slow.log

# Queries der letzten 24 Stunden filtern
grep -A 3 "Query_time" /var/log/mariadb/slow.log | grep -v "^--$"

# Log-Größe prüfen
ls -lh /var/log/mariadb/slow.log

Konfiguration: /etc/my.cnf.d/nextcloud-k3s.cnf → slow_query_log = 1, long_query_time = 1

PHP-FPM Slow Log

PHP-FPM loggt Requests, die länger als 5 Sekunden dauern, nach /proc/1/fd/2 (stderr des Pod-Hauptprozesses). Da ptrace in Containern nicht verfügbar ist, werden keine Stack-Traces geschrieben – nur der Request-Zeitstempel. 

# Slow FPM Requests verfolgen
k3s kubectl logs -n nextcloud deployment/nextcloud -c nextcloud-fpm -f | grep -i "slow"

Konfiguration: ConfigMap nextcloud-fpm-pool-config → pm.status_path = /fpm-status, slowlog = /proc/1/fd/2, request_slowlog_timeout = 5s

Betriebssystem (AlmaLinux 9)

Security-Updates werden durch dnf-automatic täglich automatisch eingespielt. Für ein vollständiges System-Update:

Details siehe Troubleshooting.

  2. Prüfen ob ein Reboot nötig ist:

Backup ausführen

Das Skript erwartet den Instanz-Namen als Argument. Die Instanz steuert welcher Server kontaktiert wird und wohin lokal gesichert wird.

Troubleshooting

Pod startet nicht / bleibt in CrashLoopBackOff

k3s kubectl describe pod -l app=nextcloud -n nextcloud
k3s kubectl logs deployment/nextcloud -c nextcloud-fpm -n nextcloud --previous

Typische Ursachen:

  • DB nicht erreichbar: MariaDB-Service läuft nicht oder nftables-Regeln fehlen (nach Reboot?)
  • config.php leer (0 Byte): Erster Start konnte config/ nicht beschreiben wegen falscher Ownership. Lösung: chown 33:33 /srv/nextcloud-www/config, leere Datei löschen, Pod neu starten.
  • Redis nicht erreichbar: systemctl status redis auf dem Host prüfen

Nextcloud-Seite lädt, aber CSS/JS fehlt (Seite sieht defekt aus)

# MIME-Typen der Assets prüfen:
curl -sI "https://nextcloud.example.com/core/css/server.css" | grep content-type
# Muss: text/css sein

curl -sI "https://nextcloud.example.com/dist/core-main.js" | grep content-type
# Muss: application/javascript sein

Ursache war in der Vergangenheit ein types {}-Block im nginx-Server-Kontext, der alle geerbten MIME-Typen überschrieben hat. Die aktuelle Konfiguration nutzt für .mjs einen dedizierten Location-Block.

"Permission denied" / "Read-only file system" bei dnf, sysctl oder /sys-Schreibzugriffen über SSH

sshds systemd-Hardening-Drop-in (common_ssh-Rolle, /etc/systemd/system/sshd.service.d/hardening.conf) setzt ProtectKernelModules=yes und ProtectKernelTunables=yes. Jede SSH-Session — auch Ansibles eigene Verbindung — läuft dadurch in einer privaten Mount-Namespace, in der /usr/lib/modules als leeres, read-only tmpfs maskiert ist und /proc/sys / /sys read-only gemountet sind. Das ist beabsichtigt (verhindert, dass ein Angreifer mit SSH-Zugriff Kernel-Module lädt oder Tunables manipuliert), bricht aber jeden Befehl, der direkt über SSH dorthin schreiben will:

  • dnf upgrade -y scheitert beim Installieren eines neuen Kernels mit einer irreführenden "nicht genug Speicherplatz auf /usr/lib/modules"-Meldung (Ansible umgeht das, indem kernel* im automatisierten Upgrade-Task der Rolle blog_packages ausgeschlossen wird; Security-Kernel-Updates landen trotzdem täglich über den dnf-automatic-Timer, der lokal läuft, nicht über SSH).
  • sysctl --system / sysctl -w ... scheitert bei fast jedem Key mit "permission denied".
  • Schreiben nach /sys/kernel/mm/transparent_hugepage/enabled (THP-Modus) scheitert mit "Read-only file system".

Fix: Befehl in systemd-run --wait --pipe -- einpacken, damit er als eigenständige Unit unter PID 1 läuft statt sshds private Namespace zu erben, z.B. systemd-run --wait --pipe -- sysctl --system. Das ist bereits in den Tasks und Handlern der Rolle common_sysctl umgesetzt. Die sshd-Härtung dafür nicht abschwächen oder entfernen — sie ist beabsichtigt.

Brotli & OCSP Stapling

Brotli und OCSP Stapling sind auf der nginx-ingress-Ebene konfiguriert und wirken für alle Domains (Nextcloud und WordPress). Brotli liefert bei typischen Nextcloud-Antworten (JSON, HTML, JS) 15–25 % kleinere Responses als gzip bei gleichem Qualitätsniveau. OCSP Stapling reduziert die TLS-Verbindungszeit um ~50–100 ms, da der Browser keinen eigenen OCSP-Request an Let's Encrypt stellen muss. 

# Brotli prüfen (br-Encoding in Accept-Encoding senden)
curl -sk --resolve nextcloud.example.com:443:127.0.0.1 \
  -H "Accept-Encoding: br, gzip" -I \
  "https://nextcloud.example.com/" | grep -i content-encoding

# OCSP Stapling prüfen
openssl s_client -connect nextcloud.example.com:443 -status 2>/dev/null | \
  grep -A5 "OCSP Response"

/tmp im RAM

Das /tmp-Verzeichnis des nextcloud-fpm-Containers ist als 64 Mi tmpfs (emptyDir: medium: Memory) gemountet. PHP-FPM schreibt dort temporäre Dateien während der Upload-Verarbeitung, der Thumbnail-Generierung und des OCC-Betriebs. Im Gegensatz zu Disk-I/O entsteht dabei keine I/O-Wartezeit.

Inhalte gehen beim Pod-Neustart verloren Alle Dateien in /tmp werden beim Neustart des Pods gelöscht. Nextcloud legt keine persistenten Daten dort ab – unvollständige Uploads werden automatisch abgebrochen und müssen neu gestartet werden.

Container- & App-Härtung

Zusätzlich zu Firewall/Fail2Ban/TLS ist jeder Container und die App selbst gehärtet – nach dem Prinzip „selbst wenn ein Angreifer irgendwo hereinkommt, soll er möglichst wenig anrichten können". Alles davon liegt offen im Ansible-Code; die Tabelle erklärt vor allem, was es jeweils verhindert.

Alle Linux-Capabilities entzogen + seccomp (RuntimeDefault) Kompromittierte Container können keine privilegierten Kernel-Operationen ausführen. Ausnahme Collabora: bewusst ohne seccomp/Capability-Drop, weil es fremde Dokumente in einer eigenen chroot/Namespace-Sandbox öffnet und dafür genau diese Syscalls braucht – dafür ist Collabora per NetworkPolicy strikt isoliert. alle Deployments – securityContext

nginx-Sperre für /occ & CLI-Endpunkte /occ hat keine .php-Endung und wurde daher als Klartext-Quellcode ausgeliefert (HTTP 200). Jetzt 403 – wie die übrigen sensiblen Pfade. next_k3s_deploy (nginx-ConfigMap)

Firewall im Detail

Das Regelwerk (/etc/nftables.conf) wird von Ansible aus dem Template common_firewall/templates/fw.nft.j2 gerendert und vom nftables-Systemd-Dienst beim Booten geladen. K3s verwaltet seine eigenen KUBE-*-Chains in iptables (getrenntes Subsystem) – es gibt keine Lock-Konflikte mit nftables.

FeatureDetail
Default-Policy DROP INPUT, OUTPUT und FORWARD haben Policy DROP – alles nicht explizit erlaubte wird verworfen
Dynamische Blocklists Native nftables Sets (banned4 / banned6) mit 24h Auto-Expiry. fail2ban schreibt erkannte Angreifer direkt in diese Sets. Prüfen: nft list set inet filter banned4
Malformed-Packet-Drop XMAS-Pakete (alle TCP-Flags gesetzt) und NULL-Pakete (keine TCP-Flags) werden sofort verworfen – typische Port-Scanner-Fingerprinting-Techniken
RST-Flood-Schutz RST-Pakete werden auf 1/s gedrosselt – verhindert RST-basierte DoS-Angriffe
Kein server_ipv4-Whitelist Die Host-eigene IP wird nur für spezifische Ports akzeptiert (Grafana :3000, kubelet-Probes :10254) – kein blanket ACCEPT, der Spoofing ermöglicht
IPv4/IPv6 in einem Regelwerk table inet deckt beide Protokollstacks ab – kein separates ip6tables erforderlich
K3s-Pflichtausnahmen INPUT: Pods → Port 6443 (K3s-API) und 10250 (kubelet/metrics-server); OUTPUT: neue Verbindungen in den Pod-CIDR (Kubelet-Liveness/Readiness-Probes). Ohne diese Regeln crashen cert-manager, coredns und metrics-server.
NodePort-Absicherung (PREROUTING) Eine prerouting-Chain (Priority raw, vor der kube-proxy-DNAT) verwirft Zugriffe auf den NodePort-Range (30000–32767) auf den öffentlichen IPv4/IPv6-Adressen. Grund: kube-proxy DNAT'et NodePorts für jede lokale Ziel-Adresse (auch die öffentliche IP) und leitet sie danach in die FORWARD-Chain – sie umgehen damit die INPUT-Regeln. Ohne diese Chain wären die Prometheus-Exporter (:30104/:30253) aus dem Internet erreichbar. Prometheus scrapt sie ausschließlich über 127.0.0.1 – localhost bleibt unberührt.

Wichtige Sicherheitshinweise

vault.yml niemals unverschlüsselt committen Vor jedem git commit prüfen: ansible-vault encrypt inventory/host_vars/test/vault.yml
MariaDB-Bind auf 0.0.0.0 MariaDB lauscht auf allen Interfaces, damit Pods via Host-IP verbinden können. Der Schutz erfolgt ausschließlich durch nftables (nur Pod-CIDR erlaubt) und den DB-User-Grant ('nextcloud'@'10.42.%'). Niemals Port 3306 öffentlich freigeben.
StrictHostKeyChecking=no in ansible.cfg Deaktiviert die Host-Key-Prüfung beim SSH-Verbindungsaufbau. Geeignet für Testserver mit wechselnden IPs, aber nicht für Produktionsserver empfohlen. Für Produktion: StrictHostKeyChecking=accept-new setzen.
