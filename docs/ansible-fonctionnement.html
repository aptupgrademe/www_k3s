Code Ansible : fonctionnement

Comment les playbooks et les rôles de ce dépôt s'articulent – pour celles et ceux qui veulent comprendre, modifier ou étendre le code. L'exploitation courante est décrite dans les guides d'exploitation (WordPress, Nextcloud).

Aperçu

Ansible est un outil « push » : une machine (le contrôleur) se connecte aux serveurs en SSH et exécute pas à pas ce que décrivent les playbooks. Aucun agent ne tourne sur les serveurs ; il leur faut seulement SSH et Python. La description est déclarative : une tâche ne dit pas « installe le paquet X » mais « le paquet X doit être présent » – s'il l'est déjà, rien ne se passe.

Contrôleur (ansible-playbook, dépôt, mot de passe du vault) │ SSH en root, port 10022 (la clé d'hôte est vérifiée) ├──► Serveur du blog blog.yml / blog-update.yml └──► Serveur Nextcloud nextcloud-k3s.yml / nextcloud-update.yml │ └─ sur chaque serveur : services hôte (nftables, SSH, fail2ban, supervision …) + K3s avec les applications en tant que workloads Kubernetes

Le dépôt gère deux types de serveurs, tous deux sous AlmaLinux 9 avec un cluster K3s à nœud unique :

  • Blog (groupe blog) : WordPress, MariaDB et Redis tournent entièrement dans K3s.
  • Nextcloud (groupe nextcloud) : Nextcloud, Collabora et notify_push tournent dans K3s, MariaDB et Redis comme services sur l'hôte.

Tout ce qui est commun – durcissement, pare-feu, supervision, K3s lui-même – se trouve dans des rôles préfixés common_, utilisés par les deux playbooks.

Inventaire & variables

L'inventaire (inventory/hosts.yml) rattache chaque serveur à un groupe. Les playbooks visent un groupe (hosts: blog) ; --limit <hôte> en choisit un serveur.

Les variables proviennent de plusieurs endroits. Si une variable est définie à plusieurs endroits, la priorité la plus haute l'emporte. Dans ce dépôt, ces niveaux comptent (du plus bas au plus haut) :

NiveauEmplacementUtilisé ici pour
1roles/<rôle>/defaults/main.ymlvaleurs par défaut d'un rôle, p. ex. clamav_profiles
2inventory/group_vars/all/*.ymlidentique pour tous les serveurs : versions, chemins, ressources par défaut
3inventory/host_vars/<hôte>/*.ymlpar serveur : noms d'hôte, IP, mots de passe, dimensionnement propre
4paramètres du rôle dans le playbook{ role: common_clamav, clamav_target: wordpress }
5register / set_factrésultats de tâches pendant l'exécution
6-e en ligne de commandel'emporte sur tout – pour les tests et les cas ponctuels
Exemple nextcloud_fpm_mem_limit: "4Gi" est défini dans group_vars/all/main.yml. Un serveur avec plus de RAM définit une valeur plus élevée dans son host_vars/<hôte>/vars.yml – elle l'emporte, car host_vars a une priorité plus haute. Les autres serveurs gardent la valeur par défaut.

L'ordre complet compte plus de 20 niveaux (documentation Ansible : « Variable precedence »). En pratique, le tableau ci-dessus suffit ; la plupart des effets difficiles à expliquer viennent d'une même variable définie à deux endroits sans le savoir.

Vault

vault.yml est chiffré avec ansible-vault. Ansible le déchiffre à l'exécution avec le mot de passe du vault (--ask-vault-pass ou un fichier .vault_pass, jamais versionné). Pour le modifier : ansible-vault edit inventory/host_vars/<hôte>/vault.yml.

Les entrées sont vérifiées

Chaque rôle qui a besoin de valeurs de host_vars les décrit dans meta/argument_specs.yml – type, description, obligatoire ou non, et no_log pour les secrets. Ansible le vérifie au démarrage du rôle : s'il manque par exemple une entrée dans le vault, l'exécution s'arrête aussitôt avec le nom de la variable au lieu d'échouer en pleine installation. « Obligatoire » ne concerne que ce que possède réellement chaque serveur qui exécute le rôle – les rôles communs comme common_grafana lisent blog_hostname sur le blog et nextcloud_hostname sur Nextcloud.

Bon à savoir Ces vérifications portent le tag always : elles s'exécutent pour tous les rôles même avec --tags …. Elles sont rapides et en lecture seule.

Versions au même endroit

inventory/group_vars/all/versions.yml contient toutes les versions installées ou déployées : K3s, Helm, Calico, les charts Helm, toutes les images de conteneurs, WP-CLI (avec somme de contrôle), les programmes de supervision et la série du dépôt MariaDB des serveurs Nextcloud. Les valeurs figurent de façon compacte en haut, les raisons et l'historique de chaque entrée en dessous.

  • Toujours exactes, jamais latest ni un tag flottant : K3s tire les images avec IfNotPresent – un tag flottant reste discrètement sur la version présente par hasard dans le cache.
  • Pas dans ce fichier : les collections Ansible (requirements.yml, où ansible-galaxy les lit) et les versions des outils de contrôle (pre-commit, GitHub Action).
  • Renovate propose les montées de version de ces lignes sous forme de pull requests (voir outils).

Les playbooks

blog.yml et nextcloud-k3s.yml

Tous deux se composent d'un play avec une liste de rôles. L'ordre est voulu :

  1. common_version_check – affiche d'abord les versions installées et disponibles.
  2. Paquets, SSH, pare-feu, sysctl, durcissement CIS – la base, avant que quoi que ce soit n'écoute.
  3. common_selinux avant le déploiement – les répertoires HostPath ont besoin de leur étiquette SELinux avant qu'un conteneur ne les utilise.
  4. common_k3s, common_calico, puis le déploiement de l'application (blog_k3s_deploy ou next_k3s_deploy). Les pods démarrent en arrière-plan.
  5. Supervision, fail2ban, mail, mises à jour automatiques, rkhunter, ClamAV, auditd, Monit – s'exécutent pendant que les pods démarrent (gain de quelques minutes).
  6. Configuration dans l'application (blog_wordpress ou next_config, via kubectl exec) – les pods sont alors prêts.
  7. *_verify – tests de fumée avec rapport en couleur et e-mail.
  8. common_aide_refresh toujours en dernier – met à jour la base AIDE pour que la vérification nocturne ne signale pas comme alarme les changements voulus de l'exécution.

Chaque rôle a un tag à son nom. --tags common_k3s,blog_k3s_deploy n'exécute que ces rôles. Les rôles fusionnés gardent les anciens tags (blog_clamav, next_selinux …) pour que les commandes habituelles continuent de fonctionner.

Les playbooks de mise à jour

blog-update.yml et nextcloud-update.yml servent aux mises à jour en production et ne touchent pas à l'hôte. Les deux exigent --limit ; Nextcloud utilise serial: 1, un serveur après l'autre, et s'arrête à la première erreur.

Pré-vérification (hors du block) en bonne santé ? sinon arrêt, rien n'est touché block: tirer à nouveau les images des Deployments, comparer les digests avec les pods en cours ne redémarrer que les Deployments dont l'image a été reconstruite (rôle common_image_refresh) Blog : lancer maintenant le job de mise à jour nocturne (dump de la base d'abord), l'évaluer Nextcloud : occ upgrade, occ app:update --all, second redémarrage pour l'OPcache vérification finale (Nextcloud : pas de mode maintenance, pas de mise à jour de base en attente) rescue: collecter l'état (occ status, pods, événements, nextcloud.log / dernier dump de la base) Nextcloud : ne désactiver le mode maintenance que si la mise à niveau elle-même est terminée s'arrêter clairement – aucun autre serveur

Rôles

Un rôle est une tâche autonome avec une arborescence fixe (voir structure). Les rôles volumineux sont découpés en fichiers thématiques que tasks/main.yml inclut avec import_tasks dans un ordre fixe (p. ex. blog_wordpress : install, security_muplugin, plugins, appearance, ai_disclosure, settings, updates).

Les rôles en détail

Chaque rôle en trois parties : Quoi – ce qu'il fait, Pourquoi – sa raison d'être, et Comment – son fonctionnement, sous forme d'enchaînement d'étapes avec les briques Ansible (→ = ensuite). L'ordre est celui des playbooks. La version détaillée, tâche par tâche, se trouve en commentaire en tête de chaque fichier sous roles/<rôle>/tasks/.

Préparation et système de base

common_version_check (les deux)

Quoi : Au début de chaque exécution, affiche les versions de K3s, Helm, nginx-ingress et cert-manager installées, fixées et nouvellement disponibles. Pourquoi : Avant chaque exécution, on voit si une version fixée dans versions.yml est dépassée ou pas encore déployée.

Comment : relever les versions (command sur le serveur, uri vers l'API GitHub) → les ramener à une même notation avec un premier set_fact (regex_search, from_json) → les comparer avec un second set_fact (== donne vrai/faux) → afficher un rapport en couleur avec debug. Lecture seule, n'interrompt jamais.

blog_packages / next_packages (par pile)

Quoi : Nom d'hôte, dépôts de paquets (EPEL ; pour Nextcloud aussi CRB et MariaDB), mise à jour du système, paquets de base. Pourquoi : Sans eux, tous les rôles suivants manquent d'outils et de dépendances.

Comment : définir le nom d'hôte (hostname) → configurer les dépôts (lire d'abord dnf repolist, n'activer que ce qui manque) → tout mettre à jour sauf le noyau (dnf name: "*" state: latest ; le noyau ne peut pas être installé depuis la session SSH confinée – ProtectKernelModules de common_ssh –, il arrive la nuit via dnf-automatic) → redémarrer si le répertoire des modules du noyau en cours a disparu (vérifié via systemd-run, la session elle-même le voit vide) ; seul le blog vérifie en plus needs-restarting -r – sur Nextcloud, ces redémarrages arrivent la nuit via dnf-automatic → installer les paquets → arrêter et masquer les services inutilisés.

common_ssh (les deux)

Quoi : SSH sur le port 10022, sshd_config durci (clés uniquement), étiquette SELinux pour le port, alarme par mail à chaque connexion interactive. Pourquoi : Retire leur base aux attaques automatisées sur le port 22 et exclut les connexions par mot de passe. Un drop-in systemd place en outre sshd dans un bac à sable dont hérite chaque session SSH : pas de modules du noyau, pas de paramètres du noyau – cela ne passe plus que délibérément par systemd-run (détails dans les docs d'exploitation, « Consignes de sécurité importantes »).

Comment : retenir s'il s'agit de la première exécution (set_fact ssh_first_run) → lire la liste des ports SELinux, ne poser l'étiquette que si nécessaire → copier la configuration et les drop-ins (copy, notify) → chaîne de handlers à la fin : vérifier avec sshd -t → redémarrer sshd (async, car la propre connexion est coupée) → reset_connection → wait_for_connection → enfin installer l'alarme de connexion : script depuis un template, timer systemd toutes les 2 minutes qui signale par mail les nouvelles connexions interactives de wtmp.

common_firewall (les deux)

Quoi : Règles nftables pour IPv4/IPv6, en option un filtre par pays pour SSH. Pourquoi : Seul ce qui est explicitement autorisé passe ; fail2ban reçoit ses ensembles de bannissement.

Comment : détecter DHCP ou statique (lire nmcli → set_fact) → construire en option la liste des pays → écrire le jeu de règles depuis le template, vérifié au préalable (template validate: nft -c) → limiter le rechargement à la propre table (drop-in systemd) → le handler recharge nftables et laisse fail2ban reposer ses bannissements (listen). Première exécution : redémarrage au lieu d'une activation à chaud (include_tasks … when).

common_sysctl (les deux)

Quoi : Paramètres du noyau (TCP BBR, délais, files d'attente, durcissement réseau CIS) et Transparent Huge Pages sur madvise. Pourquoi : Serveur web plus rapide, faiblesses réseau connues corrigées.

Comment : charger le module tcp_bbr et l'inscrire pour le démarrage → valeurs en fichiers dans /etc/sysctl.d/ (template, permanent) → appliquer immédiatement (sysctl --system via systemd-run, car la session SSH confinée ne peut pas écrire de valeurs du noyau) → une petite unité systemd règle THP à chaque démarrage.

common_cis_hardening (les deux)

Quoi : Les points du benchmark CIS applicables sans risque : AIDE, modules du noyau bloqués, journal, pas de core dumps, droits cron/sudo, options de montage. Pourquoi : Moins de surface d'attaque ; les points risqués (PAM, GRUB, politique crypto) restent volontairement de côté.

Comment : une série de petits groupes indépendants, chacun selon le schéma « vérifier l'état → ne modifier que si nécessaire » : p. ex. ne créer la base AIDE que si elle manque (stat → when) → n'écrire sudoers qu'après vérification (validate: visudo -cf) → écrire les options de montage dans fstab et les activer aussitôt (mount state: mounted).

common_selinux (les deux, profil selinux_target)

Quoi : SELinux en mode « enforcing » et les répertoires de l'hôte montés comme stockage dans les pods. Pourquoi : Les conteneurs ne peuvent écrire que dans des fichiers de type container_file_t.

Comment : choisir le profil (selinux_profiles[selinux_target]) → créer les répertoires avec propriétaire et droits (file, loop) → enregistrer la règle de façon permanente (semanage fcontext ; « already defined » ne compte ni comme erreur ni comme modification) → l'appliquer aux fichiers existants (restorecon).

Nextcloud uniquement : base de données et cache sur l'hôte

next_mariadb (Nextcloud)

Quoi : MariaDB sur l'hôte : durcissement systemd, journal des requêtes lentes, rotation, base de données, utilisateur. Pourquoi : Nextcloud a besoin d'une base de données que seuls les pods peuvent joindre.

Comment : vérifier si la base Nextcloud existe déjà (register db_check) → à la première exécution seulement : créer le mot de passe root, la base et l'utilisateur (when: db_check.rc != 0) → à chaque exécution : supprimer les comptes anonymes et la base de test, créer ou corriger l'utilisateur de l'exporteur (community.mysql, idempotent, no_log).

next_redis (Nextcloud)

Quoi : Rendre Redis joignable pour les pods et le protéger par mot de passe. Pourquoi : Redis conserve les verrous de fichiers et les sessions de Nextcloud.

Comment : vérifier que le mot de passe figure dans le vault (assert) → définir trois lignes dans redis.conf (lineinfile, notify) → redémarrer tout de suite plutôt qu'à la fin (meta: flush_handlers) → attendre que le port réponde (wait_for).

Kubernetes et l'application

common_k3s (les deux)

Quoi : K3s, Helm avec le plugin helm-diff, cert-manager (Let's Encrypt) et l'ingress F5 nginx. Les composants fournis avec K3s dont personne n'a besoin ici (Traefik, ServiceLB, local-storage) sont désactivés. Pourquoi : C'est la plateforme sur laquelle tournent le blog et Nextcloud. Ce qui ne tourne pas ne peut pas être attaqué.

Comment : lire la version installée (register) → ne télécharger le binaire que s'il diffère de k3s_version (get_url … when, notify) → redémarrer tout de suite (flush_handlers) → attendre que l'API réponde (until) → Helm de la même façon → ne télécharger helm-diff que si la version diffère de helm_diff_version (somme de contrôle dans get_url) → installer les charts (kubernetes.core.helm ne modifie qu'en cas d'autre version de chart ou d'autres valeurs).

common_calico (les deux)

Quoi : Calico en mode policy-only – Flannel continue de gérer le réseau, Calico applique les NetworkPolicies. Pourquoi : Sans Calico, toutes les NetworkPolicies seraient ignorées en silence.

Comment : rendre le template sur le contrôleur (lookup('template')) → le découper en objets Kubernetes (from_yaml_all) → appliquer via l'API (kubernetes.core.k8s apply, « changed » seulement en cas d'écart réel) → n'attendre les pods que dans ce cas (rollout status … when changed). Ce schéma d'application K8s est utilisé par 26 tâches du dépôt.

blog_k3s_deploy / next_k3s_deploy (par pile)

Quoi : Tous les objets Kubernetes de l'application : namespace, secrets, ConfigMaps, deployments, services, ingress, CronJobs, NetworkPolicies, politique d'images (pour Nextcloud en plus Collabora, notify_push, synchronisation des apps). Pourquoi : Pour que l'application puisse être reconstruite à tout moment depuis le dépôt.

Comment : un template et un fichier de tâches par composant, dans l'ordre des dépendances (import_tasks) → appliquer chacun avec le schéma d'application K8s → n'attendre les nouveaux pods que si quelque chose a changé → Nextcloud : MariaDB/Redis sur l'hôte en tant que « services externes » (service sans sélecteur + endpoints vers l'IP de l'hôte).

Supervision

common_node_exporter / common_mysqld_exporter (les deux / Nextcloud uniquement)

Quoi : Exposent localement les métriques de l'hôte ou de la MariaDB de l'hôte (127.0.0.1:9100 / :9104). Pourquoi : Prometheus les récupère là ; rien n'est joignable de l'extérieur.

Comment : lire la version installée → ne télécharger, décompresser et installer l'archive qu'en cas de version différente (get_url → unarchive → copy, ignorés en mode check) → écrire l'unité systemd + le drop-in de bac à sable (notify) → les handlers rechargent systemd et redémarrent le service une fois. L'exporteur MariaDB lit son mot de passe dans un fichier que lui seul peut lire (no_log).

common_prometheus (les deux)

Quoi : Collecte les métriques de tous les exporteurs et les conserve 30 jours, joignable uniquement en local. Pourquoi : Base des courbes et des alertes Grafana.

Comment : comme pour les exporteurs (vérifier la version → ne télécharger qu'en cas d'écart) → configuration depuis le template, qui ajoute les bons exporteurs selon la pile (template) → unité et bac à sable → exactement un redémarrage à la fin, quel que soit le nombre de fichiers modifiés (handler).

common_grafana (les deux)

Quoi : Grafana avec une source de données Prometheus, trois tableaux de bord et des alertes par mail, accessible sous /grafana/. Pourquoi : Des courbes et des alertes sans que Prometheus lui-même doive être exposé.

Comment : installer le paquet, définir des lignes isolées dans grafana.ini (lineinfile) → démarrer et attendre que l'API réponde (uri … until) → via l'API HTTP « regarder d'abord, puis créer » (enregistrer le GET → POST seulement when il manque) → télécharger et importer les tableaux de bord → règles d'alerte via un petit script Python.

Protection, mail et maintenance

common_fail2ban (les deux)

Quoi : Bannit les adresses IP qui attaquent SSH ou les connexions, ou qui sondent le système. Pourquoi : Les attaques automatisées s'arrêtent après quelques tentatives au lieu de jamais.

Comment : action de bannissement propre (écrit dans les ensembles nftables du pare-feu), cinq filtres et jail.local avec sept jails depuis des templates (template, notify) → démarrer le service → un timer recharge les jails HTTP dès que le pod ingress crée un nouveau fichier de journal.

common_msmtp (les deux)

Quoi : msmtp comme remplaçant léger de sendmail. Pourquoi : cron, rkhunter, ClamAV, dnf-automatic et les rapports de vérification peuvent envoyer des mails.

Comment : installer le paquet → /etc/msmtprc depuis le template (relais, port, identifiants du vault ; droits 0600) → créer une fois le fichier de journal (file state: touch avec preserve, pour qu'il ne compte pas comme modifié à chaque fois). Pas de service : chaque programme lance msmtp lui-même.

common_dnf_automatic (les deux)

Quoi : Installe les mises à jour de sécurité la nuit et redémarre à 03:30 si nécessaire. Pourquoi : Les failles sont corrigées sans que personne ait à y penser.

Comment : deux lignes dans automatic.conf (mises à jour de sécurité uniquement, installer réellement) → déplacer le timer à 01:00 par un drop-in (redémarré seulement si le drop-in a changé : register → is changed) → deux entrées cron : redémarrage si nécessaire et mail de contrôle à 06:00.

common_rkhunter (les deux)

Quoi : Recherche la nuit des rootkits et des fichiers système modifiés, n'envoie un mail qu'en cas de découverte. Pourquoi : Alerte précoce si le serveur a été compromis.

Comment : définir les options (lineinfile dans une loop sur clé/valeur) → construire la base de référence (--propupd) → créer l'entrée cron nocturne, supprimer l'analyse en double du paquet → plugin dnf qui renouvelle la base après chaque mise à jour (sinon fausse alerte).

common_clamav (les deux, profil clamav_target)

Quoi : Analyse antivirus nocturne des fichiers envoyés (blog : uploads, Nextcloud : données des utilisateurs), mail seulement en cas de découverte. Pourquoi : Un logiciel malveillant dans des fichiers envoyés par d'autres est repéré au plus tard le lendemain matin.

Comment : choisir le profil (set_fact clamav: profiles[target]) → télécharger une fois les signatures (creates:), ensuite le service freshclam les tient à jour → générer avec Jinja les motifs d'exclusion pour les fichiers multimédias → écrire le script d'analyse (copy avec un {% if %} Jinja) → entrée cron.

blog_visitor_stats (blog)

Quoi : Chaque nuit, compte anonymement les visiteurs de la veille à partir du journal de l'ingress et ne stocke que des chiffres. Pourquoi : Une évolution sur des mois, bien que K3s ne conserve les journaux que quelques jours – aucune IP ne quitte le serveur.

Comment : copier le script et l'outil de mise à jour de la base des pays → deux timers systemd depuis des templates (flush_handlers avant le démarrage) → une fois : télécharger la base des pays et rattraper les jours encore disponibles (creates:, loop sur 1 à 5 jours).

common_auditd (les deux)

Quoi : Le noyau journalise les opérations sensibles pour la sécurité (fichiers des utilisateurs, sudo, configuration SSH, clés K3s …). Pourquoi : Des traces pour une enquête ultérieure et un mail en cas d'événements qui ne devraient jamais se produire.

Comment : copier le fichier de règles → le handler le charge dans le noyau (augenrules --load) → script de signalement et cron toutes les dix minutes, qui n'envoie par mail que les clés critiques.

common_logrotate (les deux)

Quoi : Règles de rotation pour les journaux qui n'en ont pas ou dont les règles sont incomplètes (Grafana, Prometheus, fail2ban, rkhunter). Pourquoi : Sinon ils grossissent sans limite.

Comment : quatre tâches copy vers /etc/logrotate.d/ – pas de redémarrage nécessaire, logrotate les lit lors de sa prochaine exécution quotidienne.

common_monit (les deux)

Quoi : Chien de garde pour les services, le pare-feu, les pods, les certificats, le stockage et les sauvegardes ; redémarre fail2ban en cas de panne. Pourquoi : N'envoie un mail qu'en cas de changement d'état – chaque mail a donc un sens.

Comment : vérifier que les identifiants mail sont présents (assert) → déterminer quels services existent sur cet hôte (systemctl cat dans une loop → zip + selectattr) → scripts de vérification et configuration depuis des templates → vérifier la configuration avec monit -t → démarrer.

Configurer et vérifier l'application

blog_wordpress (blog)

Quoi : WordPress dans le pod en cours d'exécution via WP-CLI : installation, plugin de durcissement, plugins, menu/CSS, mention IA, réglages, mises à jour. Pourquoi : La configuration du blog est reproductible et les mises à jour accompagnent chaque exécution.

Comment : partout « lire l'état → ne changer que le nécessaire » : p. ex. lire une fois la liste des plugins (from_json) → n'installer que ceux qui manquent (difference), n'activer que ceux qui sont inactifs (selectattr) → écrire d'abord les fichiers PHP en .new, ne les remplacer qu'en cas de somme de contrôle différente → comparer les versions avant et après les mises à jour, ne redémarrer que dans ce cas.

next_config (Nextcloud)

Quoi : Nextcloud dans le pod en cours d'exécution via occ : domaines, URL, mail, maintenance de la base, apps Office et aperçus, connexion Collabora, politique de mots de passe. Pourquoi : Les réglages se trouvent dans le dépôt et pas seulement dans l'instance en cours.

Comment : pour chaque valeur « get → comparer → set » : lire la valeur actuelle (occ config:…:get, register) → n'écrire que when elle diffère (changed_when: true) → ainsi une exécution sans changement ne signale rien, et une valeur modifiée à la main est rétablie et affichée comme modification. En dernière étape, la même chaîne pour la politique de mots de passe (password_policy.yml) : activer l'app → lire les valeurs → supprimer les anciennes valeurs divergentes → les redéfinir avec un type (--type=integer|boolean).

blog_verify / nextcloud_verify (par pile)

Quoi : Tests de fumée après l'exécution : services, pods, HTTPS, certificat, en-têtes, chemins bloqués, base de données/cache. Pourquoi : Une exécution qui affiche « ok » ne signifie pas encore que le site fonctionne.

Comment : ne faire que collecter toutes les vérifications (register _v_*, failed_when: false) → les convertir en vrai/faux avec set_fact (_r_*) → compter, afficher le rapport, envoyer le mail → seulement tout à la fin, assert sur les points critiques. Même schéma que pour la vérification des versions : d'abord relever, puis préparer, puis juger.

common_aide_refresh (les deux)

Quoi : En dernier rôle, renouvelle la base de référence AIDE si l'exécution a modifié des fichiers surveillés. Pourquoi : Sinon AIDE signale la nuit suivante les propres modifications de l'exécution comme une découverte.

Comment : une seule analyse compare et écrit la nouvelle base (aide --update) → évaluer le code de retour (1 à 7 = différences, 0 = identique, 14 et plus = erreur) → n'activer la nouvelle base qu'en cas de différences – c'est la seule tâche qui signale « changed ».

Rôles auxiliaires (pas directement dans le playbook)

common_verify – Les vérifications communes pour l'hôte, Kubernetes et HTTP. Comment : inclus par les rôles de vérification via import_role … tasks_from, ne fait que collecter les résultats (_v_*) ; c'est le rôle appelant qui juge.

common_image_refresh – Pour les playbooks de mise à jour : quels deployments ont une image fraîchement reconstruite ? Comment : un script Python (script) retélécharge chaque image et compare le digest avec celui du pod en cours → résultat en JSON → set_fact → seul ce qui a vraiment été reconstruit est redémarré.

Ce qui se passe à l'exécution

  1. Collecte des facts – seulement gather_subset: min ; rien de plus n'est utilisé.
  2. Pour chaque rôle : d'abord la validation des arguments, puis les tâches dans l'ordre. Chaque tâche renvoie ok (rien à faire), changed (modification effectuée), skipped (condition non remplie) ou failed.
  3. Handlers : une tâche avec notify: Reload nftables ne met le handler en file d'attente que si elle renvoie changed. Les handlers s'exécutent ensemble à la fin du play – ou plus tôt quand un rôle utilise meta: flush_handlers (p. ex. K3s doit avoir redémarré avant de continuer). Plusieurs handlers peuvent réagir au même événement via listen: (recharger nftables, puis laisser fail2ban réappliquer ses bannissements).
  4. Récapitulatif (PLAY RECAP) avec ok/changed/failed par serveur, et la durée de chaque tâche.

Simulation : --check --diff

Avec --check, Ansible ne modifie rien et indique ce qu'il changerait ; --diff montre les différences. Pour que ce soit parlant ici :

  • Les simples requêtes (versions, occ config:system:get, kubectl get, systemctl is-active) ont check_mode: false et s'exécutent aussi en simulation – sinon les tâches suivantes n'auraient pas de données.
  • Les commandes qui écrivent sont ignorées. Lorsque cela masquerait un changement en attente, une tâche dédiée le signale (p. ex. « mail_smtphost would be updated »).
  • Le module k8s compare les objets Kubernetes avec le cluster par un dry run côté serveur – le diff montre exactement les champs modifiés.

Kubernetes depuis Ansible

Les applications sont des objets Kubernetes. Ansible les génère à partir de templates Jinja2 et les transmet directement à l'API K3s avec le module kubernetes.core.k8s :

- name: Redis | Apply Deployment + Service
  kubernetes.core.k8s:
    kubeconfig: "{{ k3s_kubeconfig }}"
    state: present
    apply: true
    definition: "{{ item }}"
  loop: "{{ k8s_objects if ansible_diff_mode else [k8s_objects] }}"
  loop_control:
    label: "{{ (item.kind ~ '/' ~ item.metadata.name) if item is mapping else ((item | length) ~ ' objects') }}"
  vars:
    k8s_objects: "{{ lookup('ansible.builtin.template', 'redis-deployment.yml.j2') | ansible.builtin.from_yaml_all | select | list }}"
  register: redis_apply
  • lookup('template', …) génère le template en mémoire ; from_yaml_all le découpe en objets individuels. Rien n'atterrit dans /tmp – pas même les Secrets.
  • apply: true se comporte comme kubectl apply (via l'annotation last-applied-configuration), donc compatible avec les objets existants.
  • Un appel ou un par objet : lors des exécutions normales, tous les objets d'un template partent vers l'API en un seul appel (Calico : moins de 2 secondes au lieu de ~30). Ce n'est qu'avec --diff (donc dans check-drift.sh) que la boucle tourne par objet – c'est la seule façon de montrer la modification de chaque objet, et la sortie nomme Deployment/redis, Service/redis.
  • Le module ne renvoie changed que si l'objet change vraiment. Les tâches suivantes, comme « attendre le rollout », dépendent de redis_apply.changed.
  • Les requêtes passent par kubernetes.core.k8s_info (le Secret existe-t-il déjà ?).
  • Les charts Helm (cert-manager, nginx-ingress) sont gérés par kubernetes.core.helm : il compare la version du chart et les valeurs de la release en cours, et ne met à jour qu'en cas de différence. Avec le plugin helm-diff, --check --diff montre aussi quelles valeurs du chart changeraient.
  • Prérequis sur le serveur : le paquet python3-kubernetes (installé par common_k3s) ; sur le contrôleur : la collection kubernetes.core ≥ 6.5.0 (Helm 4).

Ce qui se passe dans les conteneurs – occ pour Nextcloud, wp-cli pour WordPress (toujours en www-data) – passe toujours par k3s kubectl exec.

Idempotence & « changed »

Idempotent signifie : la deuxième exécution d'affilée ne change plus rien et renvoie partout changed=0. Ce n'est qu'à cette condition qu'un changed a un sens – et qu'une simulation montre de façon fiable ce que ferait une exécution réelle. Les modèles utilisés dans ce code :

ModèleExemple
un module plutôt qu'une commandeansible.builtin.dnf, file, template, kubernetes.core.k8s savent eux-mêmes s'il y a quelque chose à faire
creates:freshclam seulement tant que /var/lib/clamav/freshclam.dat n'existe pas
changed_when d'après la sortieocc upgrade n'est « changed » que s'il affiche « Update successful »
lire – comparer – écrireles neuf réglages mail de Nextcloud : d'abord config:system:get, puis seulement ce qui diffère ; l'utilisateur de base de l'exporter : vérifier d'abord le hash du mot de passe et les droits
changed_when: falseuniquement pour de vraies requêtes – jamais pour une commande qui écrit
Le piège Une tâche command qui écrit à chaque fois avec changed_when: false paraît inoffensive mais masque toute modification. Une tâche qui renvoie changed à chaque fois transforme chaque exécution en « dérive ». Les deux ont été éliminées ici ; scripts/check-drift.sh signale immédiatement leur retour.

Gestion des erreurs

  • ansible.builtin.assert vérifie les prérequis et s'arrête avec un message compréhensible (mise à jour sans --limit, Nextcloud en mauvaise santé, mot de passe de l'exporter absent du vault).
  • failed_when définit ce qui est une erreur – p. ex. « already installed » renvoyé par occ app:install n'en est pas une.
  • block/rescue dans les playbooks de mise à jour : si une étape du block échoue, la partie rescue s'exécute. Elle a accès à ansible_failed_task et ansible_failed_result et affiche le nom de la tâche, le message d'erreur et la sortie.
  • La pré-vérification est volontairement hors du block : le rescue ne doit traiter que des états causés par l'exécution elle-même. Si Nextcloud est déjà en mode maintenance avant, le playbook refuse au lieu de « faire le ménage ».

Secrets

  • Les mots de passe se trouvent uniquement dans vault.yml (chiffré, gitignored).
  • no_log: true sur chaque tâche qui les manipule – y compris les requêtes k8s_info sur des Secrets, car le résultat contient les données. Dans les boucles, no_log peut s'appliquer par élément (no_log: "{{ item.secret | default(false) }}").
  • Les argument specs marquent les valeurs du vault avec no_log – testé : elles n'apparaissent ni avec -vvv ni dans un message d'erreur.
  • Les Secrets Kubernetes sont générés en mémoire et transmis à l'API, jamais écrits dans un fichier sur le serveur.
  • Les valeurs passées à occ transitent par argv, pas par une ligne shell – un guillemet dans un mot de passe ne peut pas modifier la commande.
  • Avant chaque commit, gitleaks recherche clés et jetons (voir la section suivante).

Tests

tests/k8s/run.sh – les rôles Kubernetes sans serveur

Démarre K3s (même version que k3s_version) comme simple serveur d'API dans podman, applique les manifestes d'abord avec les rôles de main (l'état des serveurs), puis avec l'état de travail : simulation, exécution réelle, deuxième exécution réelle, simulation. Échoue si la deuxième exécution change encore quelque chose, si un pod serait redéployé, si une release Helm reçoit une nouvelle révision – ou si une version d'image volontairement modifiée n'est pas détectée. Aucun pod ne tourne : ce qui se passe dans les conteneurs (occ, wp-cli) ne fait pas partie de ce test.

tests/update/run.sh – cas d'erreur des playbooks de mise à jour

14 scénarios contre des substituts de kubectl/crictl : sain, image reconstruite, mode maintenance déjà actif, mise à niveau interrompue, erreur après une mise à niveau terminée, rollout bloqué, job de mise à jour en échec, blog arrêté, simulation. Sont vérifiés : le code de sortie, les commandes exécutées et le mode maintenance après coup.

scripts/check-drift.sh – sur un vrai serveur

scripts/check-drift.sh nextcloud-k3s.yml <hôte> --ask-vault-pass
scripts/check-drift.sh blog.yml <hôte> --tags blog_k3s_deploy --ask-vault-pass

Une simulation avec --check --diff ; seules les tâches qui changeraient quelque chose sont affichées, avec un diff lisible (champs de gestion de Kubernetes masqués). Code de sortie 0 = aucune dérive. Juste après une exécution réelle, le résultat doit être « NO DRIFT » – sinon une tâche n'est pas idempotente.

Méthode de travail pour une modification

  1. Modifier – rôle, template ou versions.yml.
  2. ansible-lint (s'exécute de toute façon au commit).
  3. Rôles Kubernetes concernés : tests/k8s/run.sh ; playbook de mise à jour concerné : tests/update/run.sh.
  4. scripts/check-drift.sh <playbook> <hôte> – montre ce que changera l'exécution réelle. Est-ce conforme à l'intention ?
  5. Exécution réelle, d'abord sur un seul serveur, limitée avec --tags au nécessaire.
  6. Encore une fois check-drift.sh → « NO DRIFT ».
  7. Commit (les hooks vérifient lint et secrets), push.
Mise à jour de version Lire la PR Renovate (ou sa propre modification de versions.yml) → consulter les notes de version du composant → check-drift.sh → déployer avec le tag adapté (p. ex. --tags common_k3s,blog_k3s_deploy) → fusionner.

Pièges

  • Même variable à deux endroits – vérifier la priorité (ansible -m debug -a var=… sur l'hôte montre la valeur réellement appliquée).
  • item dans des boucles imbriquées – une boucle extérieure autour d'include_role a besoin de loop_control: loop_var: …, sinon les boucles du rôle écrasent item.
  • Boucle et when – la boucle est évaluée avant la condition ; un template dans loop: doit pouvoir être généré même quand when est faux.
  • Tags et include_role – les tags ne sont hérités que par import_* (statique), pas par include_* (dynamique).
  • /tmp est en noexec (CIS) – y appeler les scripts avec sh script, ne pas les exécuter directement.
  • Noms de modules avec collection – ansible.builtin.ini_file ne « fonctionnait » que par une redirection vers community.general. ansible-lint le détecte (syntax-check[unknown-module]).
  • Entrées cron identifiées par leur name – changer le nom donne deux entrées.

Parcours d'apprentissage

  1. Lire avec un objectif : choisir un rôle (p. ex. common_clamav) et expliquer pour chaque tâche pourquoi elle est écrite ainsi – module, condition, changed_when.
  2. Vivre l'idempotence : exécuter un rôle deux fois via --tags ; la deuxième exécution doit afficher changed=0 ; puis check-drift.sh.
  3. Écrire soi-même un rôle – sans modèle, avec argument_specs, un handler et un test ; puis le comparer à un rôle existant.
  4. Outils : ansible-doc <module>, ansible <hôte> -m setup, --start-at-task, --step, -vvv.
  5. Un objectif structuré : l'examen RHCE (EX294) est un examen Ansible pratique sur RHEL, bien adapté à AlmaLinux.
