NAS hp1 – Betriebsdokumentation

Debian 13 · OpenZFS RAIDZ1 · Samba · Jenkins · Homelab · Letzte Aktualisierung: Juni 2026

Überblick

hp1 ist ein HP MicroServer Gen10 Plus V2 der als lokales Homelab-NAS auf Basis von Debian 13 (Trixie) betrieben wird. Die Infrastruktur wird vollständig über das Ansible-Playbook nas.yml verwaltet. Das Gerät befindet sich im lokalen Netzwerk (192.168.10.50) und ist nicht direkt aus dem Internet erreichbar.

nas_samba_shares steuert alles Ein neuer Eintrag in nas_samba_shares erstellt automatisch das ZFS-Dataset, den Mountpoint und die Samba-Freigabe. Keine doppelte Pflege nötig.

Playbook ausführen

Voraussetzung: md RAID aufgelöst Das Playbook bricht ab wenn /dev/md0 noch existiert. Alle Daten von /raid5 müssen vorher gesichert und das md-RAID manuell aufgelöst werden. Siehe Migrationshinweise in nas.yml.

Erstmalige Einrichtung

  1. vars.yml aus der Vorlage erstellen und befüllen: 
    cp inventory/host_vars/hp1/vars.yml.example inventory/host_vars/hp1/vars.yml
# Editieren: disk IDs, email, Samba-Passwort etc.
  2. vault.yml anlegen und verschlüsseln: 
    cp inventory/host_vars/hp1/vault.yml.example inventory/host_vars/hp1/vault.yml
# Passwörter eintragen, dann:
ansible-vault encrypt inventory/host_vars/hp1/vault.yml
  3. SSH-Key auf hp1 hinterlegen: 
    ssh-copy-id -i ~/.ssh/id_ed25519.pub raphael@192.168.10.50
  4. Playbook ausführen: 
    ansible-playbook nas.yml --ask-vault-pass

ZFS-Verwaltung

Pool-Status

# Pool-Status und Integrität
zpool status data

# Belegung
zfs list

# Komprimierungsrate prüfen
zfs get compressratio data/shared data/angelika

Monatlicher Scrub

Ein Scrub läuft automatisch am 1. des Monats um 04:00 Uhr (via Cron, eingerichtet durch nas_zed). Manuell auslösen: 

# Scrub starten
zpool scrub data

# Status beobachten
watch zpool status data

ZFS-Snapshots (manuell)

# Snapshot erstellen
zfs snapshot data/shared@$(date +%Y-%m-%d)

# Snapshots anzeigen
zfs list -t snapshot

# Snapshot wiederherstellen
zfs rollback data/shared@2026-06-01

# Snapshot löschen
zfs destroy data/shared@2026-06-01
Automatische Snapshots mit sanoid Für automatisierte Snapshots (stündlich/täglich/wöchentlich) empfiehlt sich das Tool sanoid: apt install sanoid. Dokumentation: github.com/jimsalterjrs/sanoid

Laufwerk ersetzen (im RAIDZ1-Betrieb)

# 1. Defektes Laufwerk identifizieren
zpool status data

# 2. Neues Laufwerk einbauen, dann ersetzen (by-id verwenden!)
zpool replace data \
  /dev/disk/by-id/ata-WD_Red_SA500_ALTES_ID \
  /dev/disk/by-id/ata-WD_Red_SA500_NEUES_ID

# 3. Resilvering-Status verfolgen
watch zpool status data

Troubleshooting

ZFS-Pool degradiert nach Laufwerksausfall

# Status zeigt DEGRADED
zpool status data

# Defektes Laufwerk → ersetzen (Anleitung im ZFS-Abschnitt oben)
# ZED schickt automatisch eine E-Mail bei Statusänderung

Samba-Freigabe nicht erreichbar

# Dienststatus
systemctl status smbd nmbd

# smb.conf testen
testparm -s

# ZFS-Mountpoint vorhanden?
zfs list data/shared
ls -la /raid5/shared

Jenkins-Job schlägt fehl

# Log des letzten fehlgeschlagenen Builds
cat /var/lib/jenkins/jobs/Backup-CVJM/builds/lastFailedBuild/log

# Jenkins neu starten
systemctl restart jenkins

# Backup-Skript manuell testen
sudo -u raphael /raid5/shared/shared/ablage/nextcloud_backup_and_restore/cvjm_backup_nextcloud_remote.sh

ZFS-Pool nach Reboot nicht gemountet

# Pool manuell importieren
zpool import data

# systemd-Dienste prüfen
systemctl status zfs-import-cache zfs-mount
journalctl -u zfs-import-cache --no-pager | tail -20
